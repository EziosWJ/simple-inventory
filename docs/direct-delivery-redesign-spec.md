# 独立直送单与普通销售采购来源规格

## Problem Statement

直送需要分别录采购、销售并分别过账，重复输入且存在中间状态；普通销售的一对一直送关联无法表达从多个供应商采购配件后销售给客户的来源，影响售后查询。

## Solution

提供独立直送单，一个供应商、一个客户，实物共用商品和数量、分别填采购价和销售价，支持销售侧服务。客户收货后一次确认同时生成并过账采购和销售；整笔取消后可独立新建，互不影响。普通销售另外提供按明细填写的可选、多采购来源人工追溯记录。

## User Stories

1. As an 经营者, I want 独立的直送录单入口, so that 一次录入供应商直接交付客户的业务。
2. As an 经营者, I want 一张直送单选择一个供应商和一个客户, so that 分别记录两边交易对象。
3. As an 经营者, I want 填写业务日期、备注和客户送货资料, so that 准确表达此次实际交付。
4. As an 经营者, I want 实物共用商品和数量、分别填写采购与销售价, so that 避免重复录入。
5. As an 经营者, I want 销售侧附加服务, so that 记录安装等收费而不增加采购和库存。
6. As an 经营者, I want 保存和编辑直送草稿, so that 交付前准备资料而不记账。
7. As an 经营者, I want 在客户收货后一次确认直送, so that 同时完成两边业务。
8. As an 经营者, I want 确认后自动生成并过账采购和销售, so that 减少打开两张单分别操作。
9. As an 经营者, I want 确认失败整笔回滚, so that 避免只有一边生效。
10. As an 经营者, I want 重复提交和未知结果核实, so that 不重复生成单据或记账。
11. As an 经营者, I want 商品和往来资料在确认时重新校验, so that 避免使用失效资料。
12. As an 经营者, I want 直送确认后的库存净变化为零, so that 准确表达货物不留在店内。
13. As an 经营者, I want 成对的直送采购与销售库存流水, so that 追溯历史业务。
14. As an 经营者, I want 独立的供应商应付与客户应收, so that 分别结算两边金额。
15. As an 经营者, I want 零金额直送正常确认, so that 保留实物记录而不伪造往来金额。
16. As an 经营者, I want 查询直送列表、详情及状态, so that 找到需要处理的业务。
17. As an 经营者, I want 打开生成的采购和销售, so that 查询价格、明细和操作记录。
18. As an 经营者, I want 生成两单的来源标记和独立操作限制, so that 保持直送的一致性。
19. As an 经营者, I want 从直送入口整笔取消, so that 一次冲销采购和销售。
20. As an 经营者, I want 草稿取消不记账, so that 终止未发生的业务。
21. As an 经营者, I want 取消失败整笔回滚, so that 避免只冲销一边。
22. As an 经营者, I want 取消原因、原单、原流水与审计保留, so that 查询发生过的业务。
23. As an 经营者, I want 取消后按实际情况独立新建直送单, so that 无需维护复杂更正关系。
24. As an 经营者, I want 保留原收付款、退款另行登记, so that 真实资金不因单据取消消失。
25. As an 经营者, I want 有生效退货时禁止整笔取消, so that 避免重复冲销。
26. As an 经营者, I want 客户退回店内时办理销售退货, so that 正确增加店内库存。
27. As an 经营者, I want 后续退给供应商时办理采购退货, so that 沿用现有退货闭环。
28. As an 经营者, I want 复用销售送货单打印与金额显隐, so that 让客户签收且不泄露采购价。
29. As an 经营者, I want 旧版直送保留原状态、关联和操作规则, so that 继续处理历史单据及未完成草稿。
30. As an 经营者, I want 普通销售按明细选择多个采购来源, so that 查询不同供应商的配件出处。
31. As an 经营者, I want 每个来源记录采购明细和数量, so that 比整单关联提供更明确的售后信息。
32. As an 经营者, I want 来源选填且允许部分记录, so that 继续销售历史库存。
33. As an 经营者, I want 只关联相同商品的已过账采购明细, so that 减少关联错误。
34. As an 经营者, I want 来源合计不超过该销售明细原数量, so that 避免单行填写超量。
35. As an 经营者, I want 同一采购明细被多张销售引用而不占用数量, so that 保持人工追溯的轻量模式。
36. As an 经营者, I want 采购日期晚于销售时明确确认, so that 允许补录并提醒核对。
37. As an 经营者, I want 销售过账后补填和更正来源, so that 完善售后资料。
38. As an 经营者, I want 来源修改记录操作人、时间和前后内容, so that 追溯人工更正。
39. As an 经营者, I want 来源采购取消或退货后保留关联并提示, so that 保留历史且识别来源状态变化。
40. As an 经营者, I want 来源不改变库存、往来或自动发起退货, so that 沿用原业务记账规则。
41. As an 经营者, I want 配件销售继续扣配件、整机销售继续扣整机, so that 不引入组装转换。
42. As an 经营者, I want 权限控制和双账号版本冲突提示, so that 安全共享录单工作。

## Implementation Decisions

1. 使用模块化单体与 Handler → Service → Repository；新直送业务复用采购、销售的验证、快照、库存、往来和审计能力。业务 Service 不依赖具体数据库。
2. 直送状态采用 DRAFT → POSTED / CANCELLED，单号唯一且不可变；草稿可编辑，终态锁定。乐观版本、幂等请求与可查询结果防止重复生效；新直送至少包含一条实物。
3. 双库增量 Goose migration 增加直送单及明细、生成单据来源关联、普通销售采购来源记录和必要约束、菜单与权限。不使用 AutoMigrate，不改写历史采购销售，不为旧直送伪造新业务。
4. 直送 API 提供创建、编辑、分页、详情、确认和取消，沿用版本、原因与响应信封；生成采购、销售返回来源直送 ID，便于详情跳转与禁止独立修改、过账或取消。
5. 确认必须在一个事务中生成采购、销售、过账两边、记录库存与往来、更新直送状态及写审计；先完成所需文档、往来与商品锁，再统一取实际生效时间。任何验证、余额范围、竞争或审计失败全部回滚。事务不可通过调用普通 HTTP 接口串联。
6. 采购增加、销售减少的直送库存流水同时提交，净库存为零；零金额正常过账但不生成零金额往来流水。数量三位小数、金额两位小数、行金额按现有定点规则计算并防溢出。
7. 直送取消同事务先冲销销售、再冲销采购；草稿取消不生成两边单据。只允许取消两边仍有效且无生效退货的整笔业务，重复取消不得重复冲销。保留原流水、真实收付款、历史快照与审计。
8. 取消和后来新建完全独立，不生成重开链、不继承日期价格、不限制新单交易对象。客户退回店内及后续退供应商使用现有销售退货、采购退货，已有生效退货时禁止整笔取消。
9. 原收付款不删除、不逐单重分配；按往来总余额体现欠款或待退款，实际退款独立登记。新单自行填写业务日期，各次库存与往来按实际生效时间记录。
10. 新直送统一入口，新生成两单禁止独立编辑、过账和取消；详情可查看、打印、追溯和进入现有退货路径。客户打印复用销售送货单及快照，不展示采购价。
11. 普通销售采购来源以稳定销售明细 ID 指向一个或多个采购明细并记录数量。选择时仅接受相同商品的已过账采购明细，来源数量为正、最多三位小数，单条销售明细合计不超过原销售数量。同一来源重复填写应拒绝；服务不填写实物来源。
12. 来源选填，允许部分填写，不占用采购数量、不限制跨销售累计数量、不改变库存或往来。日期晚于销售需显式确认并由 API 校验确认标记，过账后仍可更正来源；编辑销售数量或商品时同时校验已有来源，不能留下超量或错商品引用。
13. 来源更新携带销售版本、同事务写审计并保留前后记录，不能顺带修改已过账销售内容；来源已取消采购仍保留并显示当前状态与退货情况，补填或更换时重新验证新来源。显示未记录数量。
14. 旧版直送保留已有 API、关联与原操作规则，原草稿保留继续完成的界面路径；通过来源 ID 区分新旧，禁止新入口操作旧数据。普通新销售不再显示原直送选择器。
15. 复用现有列表、表单、详情 Pattern、基础资料搜索、离开提醒和确认 Dialog；并发冲突和未知结果核实保持既有交互标准。配件与整机继续现有库存模型，不增加组装功能。

## Testing Decisions

- 优先使用应用公开 HTTP API 契约作为行为验证入口，并辅以真实浏览器录单路径；不以私有函数或数据库内部实现细节作为主要断言。
- 新增 TestSQLite/TestPostgres 前缀双库契约，验证直送草稿、确认、取消、零金额、服务、库存与往来、来源更新、权限与并发、防重及审计失败回滚。
- 复用现有采购、销售、直送、退货、保存回执、EffectiveTime、ZeroAmount 与 migration 契约作为回归先例。断言业务状态、不可变记录和余额，以及两边失败无部分生效。
- 新迁移验证 PostgreSQL/SQLite 空库和含旧采购、销售、直送、退货及流水数据的升级；同步迁移版本、菜单数量断言，核对 Taskfile 与 CI 选中新契约各一次。
- 迭代先定向 SQLite 再定向 PostgreSQL；由于涉及 schema 和事务协作，收尾一次 task db:check，另执行前端 lint/build、相关浏览器验收以及固定 task api:docs，检查生成差异。
- 浏览器验证独立直送新建确认、两边跳转、整笔取消、独立再新建、退货阻止取消、旧单继续处理、多个来源与部分记录、日期确认、已过账补填及取消来源提示。打印模板未变更时复用现有打印验收。

## Out of Scope

多供应商直送单、联动重开或旧新单更正链、订单履约阶段、严格采购数量分配、库存批次、SN、组装转换、成本毛利、逐单收付款核销、自动退款、服务退费和新增打印模板。

## Further Notes

本规格根据已确认访谈及用户最新简化要求编写；用户已授权直接发布规格、任务并开始编码，因此不再要求发布或任务拆分确认。新方案覆盖新直送入口的规则，旧版历史业务仍遵循原规格。原始讨论和 ADR 用于保留决策背景，不以曾被用户撤回的联动重开方案作为需求。
