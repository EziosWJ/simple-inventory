# 业务单据详情与过账确认体验统一规格

状态：销售单详情第一轮效果已获经营者认可；本规格综合本次讨论，作为后续多 agent 实施的指导。验收边界已确认：优先使用现有浏览器测试及 mock API；实际修改 API 或数据库行为时补对应后端与双库契约。

GitHub 规格 Issue：[#90](https://github.com/EziosWJ/simple-inventory/issues/90) · `ready-for-agent`。

## Problem Statement

经营者查看入库、销售、退货及库存调整等业务单据时，重要信息与辅助字段混排，商品描述、数量、操作人与时间常被拼成一段文字。长单需要反复滚动才能了解金额和找到操作，关联单据与追溯说明有时先于本单商品出现。经营者无法迅速确认“谁的单、什么时候的业务、是否生效、有哪些商品、金额是多少”。

保存并过账等确认窗口也存在类似问题：明细多以文字列表展示，库存及往来影响不够突出，用户需要自己辨认哪些内容即将生效。若只统一外观而忽略保存成功、过账失败、响应丢失、他人修改等情况，会损害已有异常恢复能力。

销售单详情已完成并获得认可的第一轮优化，证明“概览靠前、商品为主体、辅助内容按需展开、操作位置固定”的方向可用。其他业务需要一致的指导及清晰的分工边界，使多个 agent 能沿用该方案，同时保留每类单据的业务含义。

## Solution

将已认可的销售详情作为视觉与交互基线，形成两种单据阅读模式：

1. **单据详情**：查看已保存的内容，先确认单据身份和真实状态，再核对商品、金额及业务影响，最后按需查看送货资料、来源、关联单据和操作记录。
2. **过账确认**：核对即将提交的内容，先说明执行对象和动作，再展示金额、明细以及将产生的库存／往来影响，底部提供明确的返回与确认操作。

两种模式共用信息层级、商品排版、数值对齐、固定操作区和辅助信息折叠规则，分别表达“已发生”和“将发生”。不把详情状态、确认预览或浏览器请求状态混为一谈。

### 交付范围

| 业务 | 详情范围 | 确认范围 |
| --- | --- | --- |
| 采购入库 | 采购单详情，含普通采购、旧版直送、新直送生成单 | 新建／编辑保存并过账、已保存草稿过账、现有安全重试确认 |
| 销售出库 | 保留已认可的详情基线，适配后续公共能力并做回归 | 新建／编辑保存并过账、已保存草稿过账、现有安全重试确认 |
| 采购退货 | 退货详情、原采购单追溯 | 已保存退货草稿过账 |
| 销售退货 | 退货详情、原销售单追溯 | 已保存退货草稿过账 |
| 库存调整 | 维护页详情与库存流水打开的来源详情 | 已保存调整单过账 |
| 独立直送 | 沿用独立详情页，统一其摘要、商品与辅助分区 | 客户已收货后确认，同时生成并过账采购与销售 |

退货、库存调整、独立直送不新增“保存并过账”快捷流程；统一其已经存在的确认步骤。独立直送详情仍为独立页面，不为一致性改成弹窗。

收付款、退款、期初往来等可在后续参照本方案扩展，本次不列为必做交付项。已生效单据的取消／冲销规则继续保留，涉及本次公共组件或布局时必须回归；不要求顺带重构所有取消、离开、商品切换及资料选择提示。

## User Stories

1. 作为经营者，我希望打开详情立即看到单据类型、单号、交易对方和业务日期，以便确认自己查看的是正确单据。
2. 作为经营者，我希望状态同时包含中文标签和业务说明，以便知道这张单是否已经改变库存或往来余额。
3. 作为经营者，我希望单据金额在首屏可见，以便不用先滚到明细底部才能了解业务规模。
4. 作为经营者，我希望概览显示明细项数，并在销售中区分实物与服务，以便理解交付内容。
5. 作为经营者，我希望不同单位的数量不被合计成一个总数，以便避免把台、支、次误当作可相加的数量。
6. 作为经营者，我希望商品明细先于采购来源和操作记录出现，以便先完成最常用的核对。
7. 作为经营者，我希望商品名称与编码、型号、规格分层展示，以便快速识别商品并比较规格。
8. 作为经营者，我希望数量直接附带单位，以便减少在两列之间来回对应。
9. 作为经营者，我希望单价和金额右对齐且格式一致，以便逐行核对价格和合计。
10. 作为经营者，我希望服务项目有清晰标识，以便知道它不产生库存变动。
11. 作为经营者，我希望行备注和整单备注能按原有换行阅读，以便重要交付说明不会淹没在商品文字中。
12. 作为经营者，我希望在长单中滚动明细时仍能看到操作按钮，以便随时打印、返回、编辑或进入关联业务。
13. 作为经营者，我希望送货资料和经营者抬头可以按需展开，以便查询商品时不被辅助资料打断。
14. 作为经营者，我希望采购来源显示简短摘要且可展开更正，以便保留售后追溯能力。
15. 作为经营者，我希望来源采购取消或发生退货的核对提示默认可见，以便折叠来源时仍能注意到异常。
16. 作为经营者，我希望关联单号能打开对应业务且保留来源导航，以便来回核对时不丢失查询上下文。
17. 作为经营者，我希望操作记录以创建、过账、取消的时间顺序展示，以便追溯谁在什么时候操作了单据。
18. 作为经营者，我希望已过账后冲销与草稿取消有不同说明，以便理解是否曾经产生过业务影响。
19. 作为经营者，我希望取消原因默认可见，以便立即了解当前单据为何失效。
20. 作为经营者，我希望历史商品与送货资料保持过账时的快照，以便旧单不会随当前档案变化。
21. 作为经营者，我希望详情不把单据金额当成未结欠款，以便不误认为某张采购或销售单已经结清。
22. 作为经营者，我希望纯服务和零金额单据有准确的生效说明，以便不被通用的库存／金额文案误导。
23. 作为经营者，我希望退货详情突出本次数量与金额，并明确标注原数量、有效已退数量和剩余额度，以便避免读错退货范围。
24. 作为经营者，我希望从退货单直接进入原单，以便核对原成交内容和价格。
25. 作为经营者，我希望退货过账与实际退款分别表达，以便知道抵减往来余额并不代表资金已经退回。
26. 作为经营者，我希望库存调整突出增加／减少数量、调整原因和已有的前后余额，以便直观了解调整影响。
27. 作为经营者，我希望库存流水打开的调整详情与维护页使用一致的阅读结构，以便不需要重新学习相同单据。
28. 作为经营者，我希望直送详情清楚展示供应商、客户、采购金额和销售金额，以便核对同一笔直送的两侧业务。
29. 作为经营者，我希望新直送生成单指向统一操作入口，旧版直送保留原有规则，以便不把两种流程混用。
30. 作为经营者，我希望保存并过账前看到将提交的对象、日期、商品、数量、单价和合计，以便发现错误后返回修改。
31. 作为经营者，我希望确认弹窗明确说明每种实物的库存方向和数量，以及客户／供应商往来金额的方向，以便知道确认的实际后果。
32. 作为经营者，我希望同商品分行保留成交明细，同时库存影响按商品身份与单位合并，以便核对价格与库存两种视角。
33. 作为经营者，我希望关闭或返回确认时不保存、不提交过账，以便可以安心重新检查输入。
34. 作为经营者，我希望提交中避免重复确认，并看到正在保存还是正在过账，以便理解当前进度。
35. 作为经营者，我希望保存失败时不继续过账，以便错误输入不会产生库存或往来变动。
36. 作为经营者，我希望保存成功而过账失败时保留同一草稿、单号和输入，并明确告知原因，以便修正后继续处理。
37. 作为经营者，我希望响应丢失时保留待核实状态并沿用现有核实入口，以便不会误报失败或重复建单。
38. 作为经营者，我希望他人修改或取消单据后停止旧确认，以便不会在不知情时过账新内容。
39. 作为经营者，我希望确认直送前看到“客户已收货”的依据和两侧同时生效的说明，以便正确使用直送确认。
40. 作为经营者，我希望确认过账中的错误和关键警告默认可见，以便不用展开辅助区才能发现不能提交的原因。
41. 作为经营者，我希望窄窗口和短屏幕仍能阅读明细及访问按钮，以便日常电脑窗口缩小时也能完成操作。
42. 作为使用键盘的经营者，我希望折叠、关闭和确认具有合理焦点顺序，以便不用鼠标也能核对单据。
43. 作为实施 agent，我希望公共组件职责与业务模块职责明确，以便复用布局时不改变领域规则。
44. 作为实施 agent，我希望有按业务划分的独立交付与验收清单，以便多个工作树能够安全并行并顺序集成。

## Implementation Decisions

### D01. 已认可基线与统一原则

- 采用当前销售详情的蓝灰、中性、专业、弱装饰风格，复用项目已有色彩、字体、间距、圆角和按钮规范。颜色表达状态或动作，不用于无意义装饰；不新增营销风格、渐变或动效。
- 默认正文 14px、辅助信息 12–13px、区块标题 16–18px、概览金额约 24px；模块间距 24px、紧密字段间距 8–12px。数字采用等宽数字，正文左对齐，金额与数量右对齐。
- 采用“概览 → 本单明细 → 备注 → 按需辅助信息”的顺序，重要内容不藏在标签页里，不将每组字段包装成同级指标卡片。
- 当前销售详情已经实现第一轮布局、服务与零金额说明、单号复制、辅助信息折叠、固定操作区及定向浏览器回归。后续应复用和完善，不另做与认可效果不同的销售详情。
- 销售基线目前仍是工作区的未提交改动。并行实施前，由集成人将其纳入共同基线或明确分发到各独立工作树；不能假设从当前 HEAD 创建的工作树已经含有这些改动。

### D02. 弹窗与详情页结构

| 区域 | 单据详情 | 过账确认 |
| --- | --- | --- |
| 固定头部 | 类型、单号、中文状态、客户／供应商、业务日期、交付方式 | 动作名称、执行对象、单号（已有时）、客户／供应商、业务日期 |
| 概览 | 原单金额或业务金额、项数、真实状态及影响说明 | 将提交的金额、项数、即将生效的库存／往来影响 |
| 主体 | 当前单据的商品／服务明细及合计 | 本次将提交或将过账的明细及合计 |
| 常显补充 | 有内容的整单备注、取消原因、关键异常 | 影响说明、错误、版本冲突及阻止提交的原因 |
| 可折叠辅助 | 送货及抬头、采购来源、关联单据、操作记录 | 非阻断的送货补充、来源参考或其他辅助资料 |
| 固定底部 | 状态允许的现有业务操作、来源返回入口 | 返回修改／取消确认、明确命名的确认动作 |

- 多明细单据桌面弹窗宽度上限以 1100px 为基准，受视口约束；高度上限 90dvh。头部与底部不随正文滚动，只有正文垂直滚动。简短无明细确认沿用较小宽度，不要求所有弹窗放大。
- 小于 640px 的单据弹窗使用全屏布局；表格保持容器内横向滚动。该要求是窗口溢出保护，不扩大为完整移动端产品建设。
- 不在正文中再套一个固定高度的纵向明细滚动框；横向表格容器可保留。确认按钮、错误及正文内容不能被裁切在视口外。
- 内容不足时自然收缩，不强制每张短单占满高度。头部字段支持换行，长客户名、长单号、长地址不撑破宽度。
- 独立直送详情页保留页面载体，按相同信息层级分区；其操作保持清晰可访问，不引入整个页面变成弹窗或全站固定页脚的改造。

### D03. 共用展示能力与业务边界

- 优先扩展现有 `DetailDialog`、`FormDialog`、`ConfirmDialog`、`DataTable`、`StatusTag`、`Button` 与 Dialog primitives。销售详情现有的 `fixedFooter` 是可选能力，未接入页面的默认行为不变。
- 公共层负责容器、头部／正文／操作区、展示密度和必要的折叠布局；不自行拉取业务数据、不决定能否过账／退货／冲销、不执行保存或计算真实库存与往来余额。
- 跨多个接入业务确有复用时，可抽取轻量的单据摘要、辅助折叠区和只读明细展示；接口以显式内容与回调表达，不建设配置驱动的单据引擎，不强迫所有业务使用完全相同的列。
- 业务模块继续负责字段、数据、状态、权限、价格与数量精度、快照、操作入口、错误解释和提交恢复。
- 过账预览使用同一次确认对应的表单内容或已保存单据版本。展示与提交必须一致；不能展示编辑后的新内容却提交旧预览，也不能确认旧内容后自动过账他人修改的新版本。
- 对已保存单据展示已有快照，对未保存确认展示当前准备提交的内容；不要为排版从当前档案覆盖历史单据。已有 ID、版本和恢复标识可用于处理流程，但不占据普通用户首屏。
- 公共组件变更必须 opt-in 或保持既有调用的兼容行为。项目的公共弹窗也用于系统管理页面，不能因本规格改变所有系统表单与确认窗口的大小和关闭行为。

### D04. 商品、金额、备注与状态

- 商品名称为主行，编码、型号、规格为辅行；可省略空辅助值。数量与单位同格，例如“2.5 台”；成交单价、行金额分别显示人民币符号，使用既有定点金额规则，不使用浮点数重算业务金额。
- 明细项数指行数；实物／服务项数分别计行。商品相同但单价或备注不同的成交明细不因概览而合并。
- 行备注、整单备注保留换行。超长文字可以展开全文，但不能只有无法访问的截断或 hover 提示；关键风险提示不得折叠。
- 状态使用“草稿”“已过账”“已取消”等中文标签，并说明业务含义。草稿未生效；已过账锁定内容；取消根据是否曾过账区分草稿终止与反向冲销。业务日期与实际过账时间分别标注。
- 已取消单据仍展示原明细和原金额，金额旁注明“原单”，不清零、不删除、不伪装成当前有效交易额。取消原因默认可见，记录归入可展开时间线。
- 零金额仍可以完成有实物的库存过账；其往来金额无变化。纯服务销售无库存影响；不能套用“实物已出库”。
- 单号复制沿用销售基线；成功有反馈，失败有可执行的手动复制提示。新建尚未保存时显示“新单待保存”，不编造正式单号。

### D05. 单据详情的业务差异

| 类型 | 概览与核心字段 | 业务影响与操作约束 |
| --- | --- | --- |
| 采购入库 | 供应商、业务日期、原单金额、商品项数 | 普通过账增加实物库存，供应商方向往来余额增加；草稿提供已有编辑／过账入口，已过账提供已有退货入口；零金额说明往来无变化 |
| 销售出库 | 客户、业务日期、原单金额、实物／服务项数 | 普通销售实物减少库存、服务不变，客户方向往来余额增加；已过账突出打印，纯服务不显示实物退货入口 |
| 采购退货 | 供应商、可点击原采购单号、本次退货金额、本次数量 | 过账减少实物库存并抵减供应商方向往来余额；退款另行办理，不声称供应商已经退钱 |
| 销售退货 | 客户、可点击原销售单号、本次退货金额、本次数量 | 过账增加实物库存并抵减客户方向往来余额；退款另行办理，不声称已向客户退款 |
| 库存调整 | 单号、状态、增加／减少明细项数、逐行调整原因与数量 | 数量正负与“增加／减少”文字同时表达；已有真实前后余额时展示“调整前 → 调整后”，不产生应收应付 |
| 独立直送 | 供应商与客户、业务日期、采购合计与销售合计、实物／服务明细 | 客户已收货后确认；同事务生成并过账两单，实物库存有成对流水、净变化为零，两侧往来分别增加；服务无采购库存影响 |

- “客户／供应商方向往来余额增加”是金额影响，不等同于当前欠款始终增加：余额可能从待退款变为欠款。详情与确认优先使用准确的方向文案，不伪造当前余额或前后余额。
- 当前单据金额不能解释为已收、已付、未结、待付款或已结清。系统按往来单位总余额收付款，不做逐单核销；同一单位客户与供应商方向不能自动抵扣。查看往来时沿用正确方向。
- 退货数量明确标注“原单数量”“当前有效已退数量”“当前剩余可退数量”“本次退货数量”，不得仅用斜杠拼成无标签数字串。累计额度是当前有效过账口径，本次已过账退货可能包含在累计值中，禁止重复加一次；历史退货的本次数量／金额与当前额度分开表达。
- 原明细内部 ID 从默认表格移除，以商品、原单链接和数量关系帮助核对。原成交单价、退货取整差额与后端金额口径保持不变。
- 库存调整的维护详情与来源详情都接入相同阅读层级，保留各入口已有业务操作差异。只在数据确有前后余额时展示；草稿不能通过当前库存推算“实际调整后”。
- 新直送生成的采购、销售将统一确认／取消引导到来源直送单，不开放各自独立过账／整单取消。旧版直送仍使用先采购后销售分别过账、按原约束取消的规则，相关说明默认可见。
- 已有生效退货禁止直送整笔取消，保留当前提示和链接。直送退货追溯中的必要顺序与警告不得被折叠隐藏；完整关联明细可以折叠。

### D06. 辅助信息与操作组织

- 送货资料、经营者抬头、采购来源、关联单据与操作记录默认折叠，摘要说明内容或记录数量；没有内容的资料分区不显示空占位卡片。
- 来源缺失不等于库存不足或采购数量被占用。采购来源是人工追溯参考，不参与库存分配；来源采购取消或发生退货时显示核对提示，不能阻断本来允许的业务操作。
- 关联区优先呈现单号、类型、状态与已有金额，不在当前单据前铺开所有关联明细。允许进入来源详情，保留现有来源返回与查询条件语义。
- 当前单据取消原因、来源异常、直送退货必要顺序、过账错误及冲突默认可见；可折叠区域不得成为唯一承载这些信息的位置。
- 操作时间线按创建 → 过账 → 取消顺序展示操作人和实际时间，没有发生的节点不伪造。缺失时间显示明确占位，不以业务日期代替。
- 底部只呈现当前状态、权限与既有业务规则允许的操作，最多一个视觉主按钮；打印、编辑、来源直送等根据具体任务确定主次。保留已存在操作能力，不为统一布局自动新增业务操作。
- 若已有整单取消／冲销进入同一操作区，用次级或“更多操作”入口组织，最终确认仍表达影响、要求既有原因并保留危险样式；不得与正常退货混为同一个动作。

### D07. 过账确认结构与影响表达

- 多明细确认使用与详情一致的只读表格，不再把整单商品、数量、单价、金额拼成段落或浏览器原生确认文字。
- 确认主体必须默认可见：对象、业务日期、明细、合计、库存影响、往来影响、执行动作和失败恢复说明。送货补充资料可折叠，但不能代替实际将提交的字段。
- 库存影响按商品内部身份与单位合并，不能按名称合并；同商品不同成交价格仍保留各行销售／采购明细。每个影响显示“增加／减少 + 数量 + 单位”，无实物时说明库存无变化，不将不同商品和单位求总量。
- 原单详情中的“实物已出库”在确认模式中改成“确认后将减少库存”；尚未提交时不得展示“已过账”“已收货确认成功”等完成文案。
- 采购确认表达增加库存及供应商方向往来余额；销售确认表达实物减少、服务无库存及客户方向往来余额增加；零金额明确往来无变化。
- 退货确认突出本次数量、原价及金额，分别说明入库／出库方向及往来抵减，保留额度在过账时复核、不自动退款的事实。
- 库存调整确认保留正负数量、调整原因、增加／减少项数及现有整单核对勾选，不为了与销售一致删除已有核对条件。明确库存不足或超出范围时整单拒绝。
- 独立直送确认展示供应商 → 客户、采购与销售两侧金额、核对明细及客户已收货依据；说明同事务两侧过账、库存净变化为零但保留成对流水。
- 已有草稿过账采用“确认过账”；保存并过账采用“确认保存并过账”；安全重试采用“确认重试过账”等与实际执行相符的文案。返回操作优先命名为“返回修改”或“返回核对”，不让用户误以为会取消业务单据。
- 替换范围内的原生过账确认时复用业务提交入口，只改变确认 UI 与必要的选择状态；不替换范围外的商品切换、重新加载、离开或取消提示。

### D08. 保存、过账与异常恢复不变量

本规格调整展示，不重新定义后端状态或交易流程。以下为必须保留和验收的外部行为，不要求新增通用状态机：

| 场景 | 用户必须看到的结果 | 不允许的行为 |
| --- | --- | --- |
| 尚未确认／返回修改／关闭确认 | 输入保留，未发出保存或过账写请求 | 开窗或关闭触发自动保存、自动过账 |
| 正在保存 | 正在保存、操作禁用，已有离开保护生效 | 重复点击产生多次保存、处理时随意关闭确认 |
| 保存失败且结果确定 | 保存失败原因，输入保留，不进入过账 | 继续过账、清空输入 |
| 保存成功、正在过账 | 显示已保存的正式单号及正在过账 | 把“草稿已保存”当作整单业务已经生效 |
| 保存成功、过账被确定拒绝 | 同一单号仍为草稿，具体原因，允许修正后重新确认 | 删除草稿、另建单、回滚已成功保存 |
| 保存／过账响应丢失或结果未知 | 明确待核实，沿用现有核实与恢复入口 | 仅因网络异常报“未生效”、盲目新建或重放 |
| 核实已经过账 | 展示真实已过账状态及现有后续操作 | 再次保存或再次制造库存／往来效果 |
| 核实版本已变或已取消 | 停止旧确认，提示重新加载并核对 | 自动沿用新版本过账、擅自覆盖他人修改 |
| 允许安全重试 | 沿用既有原单 ID、版本、保存回执与恢复语义 | 将重试伪装成新单或修改恢复协议 |

- 保存成功后的过账使用返回的同一单据与版本；保存／过账各自的已有事务、审计与恢复机制保持原样。独立直送继续沿用其同事务两侧生效机制。
- 加载中禁用重复提交、关闭按钮、Escape 与遮罩关闭，保留明确的阶段文案；处理离开页面时沿用已有离开确认，顶层离开决策不能被底层焦点捕获或遮罩盖住。
- 当前业务流程在失败后返回编辑页显示反馈时，可以保留该载体；不强制把所有结果反馈留在确认弹窗内。要求失败原因、正式单号与下一步在用户当前页面可见。
- 本任务不增加自动重试、后台提交、逐单结算或新的事务边界。若确实需要改变请求或恢复流程，作为明确的额外业务变更记录并补对应契约，不能混入样式任务。

### D09. 数据接口与缺失数据

- 基础统一任务使用现有详情、草稿、表单预览与过账接口，不新增 schema、migration 或强制新 REST API。公共组件不推断数据库状态。
- 原单金额继续表示原单内容。有效退货金额、净销售／净采购、关联退货汇总不作为本轮必做字段：当前采购／销售详情不直接携带完整汇总，不能用缺少信息的前端结果假装为零退货。
- 未来补该类汇总时作为独立数据任务，以有效已过账且未取消的退货为口径，草稿和取消记录不计入；保留原成交金额与数量，并补读 API、权限、响应文档及定向双库契约。
- 缺失资料省略或显示“未填写／—”，暂不可读取显示加载或失败，不能把读取失败当成“没有来源／没有退货／没有影响”。
- 金额、数量、商品快照、业务日期、实际生效时间、审计与权限继续以现有领域模型和接口为准。遵守按往来总余额结算、直送入口与人工来源、业务写入和审计原子提交等已有 ADR。

### D10. 多 agent 分工与集成

以下为可独立派发的工作包，不是已经发布的子 Issue。本规格发布不自动启动这些任务。

| 工作包 | 独占职责 | 前置依赖 | 最小交付与验收 |
| --- | --- | --- | --- |
| A0 公共能力与基线 | 公共详情／表单／确认容器、确需共享的单据展示能力、公共视觉规则及共同测试设施 | 已认可销售改动纳入共享基线 | 固定操作区、正文独立滚动、兼容默认调用；销售基线和至少一个过账确认接入证明接口可用；形成明确调用约定 |
| A1 采购 | 采购详情、采购录单保存并过账确认、采购列表过账确认、采购专属测试 | A0 | 供应商与库存／往来方向准确；普通／旧直送／新生成单；保存失败、过账失败和重试展示 |
| A2 销售 | 销售录单保存并过账确认、销售列表过账确认、销售详情的必要公共适配、销售专属测试 | A0；保持认可基线 | 混合实物服务、纯服务、零金额、同商品分行；打印、退货、来源与结果核实回归 |
| A3 退货 | 采购和销售退货详情、原单追溯、两类退货过账确认、退货专属测试 | A0 | 数量关系有标签，本次金额突出；原单可追溯；取消／草稿不计有效额度；退款语义准确 |
| A4 库存调整 | 调整维护详情、来源详情、调整过账确认、调整专属测试 | A0 | 正负与原因明确，已有前后余额正确；两个详情入口一致；核对勾选、失败及冲突仍生效 |
| A5 直送 | 独立直送详情页、直送确认 UI、追溯展示中的必要提示、直送专属测试 | A0 | 两侧对象与金额、客户收货依据、库存净零；统一入口、待核实、生效退货限制与旧版差异 |
| A6 集成验收 | 顺序集成、共用回归脚本最终收敛、跨模块浏览器验收及交付记录 | A1–A5 | 统一视觉与字段语义，相关前端门禁、各工作包测试及来源导航串联通过 |

- A0 一人负责公共组件及共用测试脚本，并以采购或销售中的一个确认场景验证接口；完成后交接该场景的业务文件归属，A1／A2再开始修改相应业务文件。
- A1–A5 在独立工作树并行实施。派发前明确业务文件、组件与测试归属；各包使用自己的定向浏览器脚本，或由公共测试负责人顺序收敛测试修改，不能同时编辑同一共用脚本。
- A5 涉及的共享直送追溯展示由其独占，其他包通过已有接口接入。共享采购来源展示能力由 A0 负责，销售包负责销售详情接入与语义回归；需要改共享接口时先向公共负责人提出具体需求。
- 业务包发现公共能力缺口时反馈 A0，由公共负责人顺序修改与交接；不能在各模块复制另一个 Dialog 框架或各自扩展相同公共文件。
- 每个包的交付说明包含改动范围、实际已跑测试、截图或可复现路径、未执行项及原因。集成人按业务包顺序集成，保留已有用户改动，不合并未经检查的整批工作树。
- 推荐先完成 A0，再并行 A1–A5，最后 A6。A1–A5 无人为采购→销售等串行依赖；真实共用能力或同文件冲突才构成阻塞。

## Testing Decisions

### T01. 已确认测试入口

- 首选最高层现有入口：真实浏览器操作 + mock API。通过用户看到的文字、状态、按钮、导航、请求次数与请求对象，以及元素实际位置验证行为，不测试内部 Hook、CSS class 名或组件私有实现。
- 沿用现有业务 UI 浏览器回归、销售详情定向回归、保存请求失败保护、销售保存并过账异常恢复及直送浏览器验收的夹具与操作方式。纯布局任务无需创建新的后端 seam。
- 对纯展示任务，mock API 模拟成功、确定失败、响应丢失、待核实、版本变化与恢复场景，验证现有交互和请求行为得到保留；不将 mock 通过描述为真实数据库事务或并发正确性已经验证。
- 只在实际改动 API／数据库行为时，补公开 HTTP 与受影响契约验证，先定向 SQLite 再定向 PostgreSQL，并按仓库分层选择后端检查、API 文档或全量数据库门禁。

### T02. 通用验收矩阵

1. **信息顺序**：打开后首先看到单据身份、金额／调整概览与状态；商品明细在辅助来源和操作记录之前。关闭再打开不同单据不会沿用前一张单的展开状态或复制反馈。
2. **状态与金额**：草稿、已过账、草稿取消、过账后冲销分别验证；原单金额、零金额、纯服务的文案准确，不出现单据结清、自动退款或混合单位总数量。
3. **长文本**：长商品名、编码、型号、规格、客户名、地址、多行备注和取消原因不会撑破视口，能够读到完整内容。
4. **长单与短屏**：使用至少 24 行明细和 1024×600 视口；正文真实产生滚动，滚到末尾前后底部操作位置不变，按钮均在视口内；避免点击自动滚动掩盖操作原本不可见的问题。
5. **宽度保护**：1440px、1024px 与 750px 检查桌面及窄窗口，390px 做溢出与全屏保护检查。商品表格仅在自己的容器内横向滚动，页面／弹窗不被撑宽。
6. **折叠**：辅助区默认收起，点击／键盘可展开，关键风险与取消原因在收起时仍可见。加载失败或空数据有区别，不能把失败显示成无记录。
7. **导航与权限**：原单、来源直送、采购来源、客户／供应商往来及打印使用正确目标；来源返回恢复既有查询上下文；无权限或非法状态不因移动按钮而暴露新能力。
8. **键盘与多层弹窗**：焦点可见、顺序合理，确认关闭恢复合理焦点；处理时不允许重复点击、Escape 或遮罩关闭；顶层离开保护出现时底层不争抢焦点或先执行退出。
9. **历史资料**：修改当前商品或送货档案后，历史详情仍使用 mock 返回的历史快照；不以当前基础档案替代。
10. **公共兼容**：至少回归一个非业务系统表单和一个普通确认调用，未启用单据模式时不被扩大尺寸、固定操作区或改变关闭行为。

### T03. 各业务必测差异

| 业务包 | 必测场景 |
| --- | --- |
| 采购 | 普通、零金额、同商品不同价分行、旧直送、新直送生成单、原备注与取消时间仍可查看、正确供应商往来方向 |
| 销售 | 混合实物／服务、纯服务零金额、同商品分行库存影响合并、来源缺失／取消／退货提示、打印、实物退货入口、销售基线效果保持 |
| 退货 | 本次与累计额度有标签、有效额度不会重复加本次、原单跳转、草稿／取消记录、原价与取整差额、两侧库存与往来方向、退货未自动退款 |
| 库存调整 | 增加、减少、多单位、多原因、有／无前后余额、两个详情入口、过账核对勾选、库存不足整单拒绝及版本冲突展示 |
| 直送 | 客户收货确认、采购／销售两侧金额及对象、服务行无采购影响、新生成单统一入口、旧直送差异、已有生效退货禁整笔取消、待核实与按原版本重试 |

### T04. 确认流程必测

- 打开、返回修改、Escape、遮罩或关闭确认不产生写请求；处理开始后取消与重复提交不可用。
- 保存确定失败：只出现原保存请求，不出现过账请求，输入保留。
- 保存成功、过账确定失败：显示同一正式单号、草稿、原因；后续修正／重试沿用同一 ID，未额外创建单据。
- 保存／过账响应丢失：进入现有待核实流程；核实为已过账时展示真实成功；无法核实时继续待核实，不误报未生效。
- 确认前后他人修改／取消或版本冲突：旧确认停止，不能自动过账新版本；重新加载必须重新核对。
- 同商品多行与不同单位：成交明细保留，库存影响按商品身份与单位正确分组；金额使用既有精度。
- 仅服务／零金额／直送：影响文案符合实际请求语义，不创建新的业务流程或恢复协议。

### T05. 检查与交付证据

- 每个前端工作包收尾运行前端 lint、前端 build、相关定向浏览器脚本及差异空白检查。公共变更由 A0／A6 负责跨调用回归，相关代码未变化的通过结果在同一批次可复用。
- 至少提供一张代表性详情截图、一张过账确认截图及长单／窄窗口的检查证据。使用 mock 或隔离数据，不修改经营者真实业务数据来制造验收场景。
- 记录实际通过、失败、SKIP、无匹配及未执行项；定向浏览器通过不等于全业务／真实双库通过。现有全量业务 UI 曾在库存调整商品筛选处超时，不能因本轮定向通过而将该全量失败改记为通过。
