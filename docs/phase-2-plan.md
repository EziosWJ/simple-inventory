# Phase 2 基础资料需求讨论记录

本文件记录需求访谈中已经确认的范围与规则。业务访谈已完成，完整规格见 [Phase 2 基础资料规格](phase-2-spec.md)，已发布为 [GitHub issue #1](https://github.com/EziosWJ/simple-inventory/issues/1)。

## 已确认

- 使用方：经营者本人，小型个体户。
- 上游：多为同行。
- 客户：国企、事业单位、部分私企和个人。
- 本轮交付：商品、客户/供应商、仓库的基础资料维护（Phase 2）。
- 库存、采购入库、销售出库仍属于后续阶段。
- 实物商品范围：硒鼓、打印机、内存、硬盘、整机等。
- 安装、维修等服务项目纳入本轮基础资料，供后续销售单选择；可填写销售价格，不产生库存。
- 不同规格分别建档，通过名称、品牌、型号、规格描述商品，不做复杂规格组合；整机作为可销售成品建档，本轮不实现组装配件消耗。
- 每项商品或服务使用一个基本单位，例如支、台、条、块、次或小时；数量允许小数，本轮不做包装自动换算。
- 往来单位使用统一档案，同一档案可以同时具有客户和供应商身份，见 [ADR-0011](adr/0011-unified-partner-records.md)。
- 往来单位支持单位/个人分类、一个主要联系人、电话、地址、备注；个人客户允许仅填名称（身份及分类仍由页面选择或默认）。
- 开票资料选填：开票名称、税号、注册地址及电话、开户行、账号；不将开票资料作为个人客户建档的前提。
- 只考虑一个逻辑仓库，不按实际存货地点拆分。
- 商品额外资料：可选分类名称（普通文本，不做分类树）、参考采购价、参考销售价、备注。
- 价格统一人民币、保留两位小数、允许不填；参考价用于后续填单，不代表库存成本。数量保留三位小数。
- 商品、往来单位编码由系统自动生成，也允许手动填写；编码唯一，名称允许重复。商品列表展示型号和规格，便于区分同名资料。
- 本轮不记录逐台实物序列号，不实现 SN 销售去向或保修追踪；相关需求留到出入库阶段再明确。
- 商品与往来单位支持编辑、停用、重新启用；本轮不提供删除。停用资料保留，后续新单据不能选择。
- 预置一个默认仓库，只允许修改名称、备注，不提供新增、删除、停用。
- 本轮通过手工新增、编辑、分页查询和筛选维护资料，不实现导入导出。

## 已确认的补充规则

用户已确认以下补充规则：

- 权限：沿用现有 JWT 登录认证与菜单角色授权，不新增 API 按操作权限编码校验；所有已登录账号均可访问本轮业务接口。不得将前端 mock 权限工具当作真实授权。
- 建档校验：商品/服务必填名称、类型、基本单位；往来单位必填名称、单位/个人分类，并至少具备客户或供应商一种身份。编码为空时自动生成，其他业务资料选填。
- 参考价允许为空或零，不允许负数或超过两位小数；资料默认启用，名称、编码去除首尾空白，不接受纯空白必填值。
- 商品与往来单位的编码在各自档案范围内唯一；手工编码统一大写，同名记录允许存在。
- 本阶段允许修改编码、商品/服务类型、基本单位，便于纠正初始录入错误；持久身份使用内部 ID。后续接入业务单据时再落实已引用档案的修改限制。

## 实施草案

### 页面与资料

复用现有管理布局、表格/表单 Pattern，提供三个业务入口：

| 页面 | 资料与操作 | 查询 |
| --- | --- | --- |
| 商品与服务 | 新增、编辑、详情、停用、启用；编码、名称、实物/服务类型、品牌、型号、规格、分类名称、基本单位、参考采购价、参考销售价、备注 | 关键词（编码、名称、品牌、型号、规格）、类型、分类、启用状态；分页 |
| 往来单位 | 新增、编辑、详情、停用、启用；编码、名称、单位/个人分类、客户/供应商身份、主要联系人、电话、地址、备注、可选开票资料 | 关键词（编码、名称、联系人、电话）、单位/个人分类、客户/供应商身份、启用状态；分页 |
| 仓库 | 展示并编辑唯一仓库的名称、备注 | 不提供多仓列表与新增、删除、停用 |

客户端与服务端均校验输入，后端与数据库唯一约束保证编码不重复；重复提交或并发请求不能产生重复编码。输入表单中明确区分空参考价与零参考价。

### 模块与 API

后端按既定架构新增 `product`、`partner`、`warehouse` 模块，在 `internal/app` 显式组装。Service 负责业务规则，通过 Repository 完成持久化与事务，不依赖 Gin、GORM 或具体数据库。

新增业务接口统一使用 `/api/v1/**`；下面是接口草案，参数与返回体需在实现时同步源注解并重新生成 Swagger：

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| GET / POST | `/api/v1/products` | 分页查询 / 新增商品或服务 |
| GET / PUT | `/api/v1/products/:id` | 详情 / 编辑 |
| PUT | `/api/v1/products/:id/status` | 启用或停用 |
| GET / POST | `/api/v1/partners` | 分页查询 / 新增往来单位 |
| GET / PUT | `/api/v1/partners/:id` | 详情 / 编辑 |
| PUT | `/api/v1/partners/:id/status` | 启用或停用 |
| GET / PUT | `/api/v1/warehouse` | 查询 / 编辑唯一仓库 |

不提供删除接口。状态接口设置明确的目标状态，重复设置相同状态仍保持一致，不使用 toggle。查询沿用现有分页参数和响应约定，不将实物数量、库存余额或单据字段加入基础资料。

### 持久化与审计

- PostgreSQL 与 SQLite 分别新增逻辑版本同步的 Goose schema migration，以及业务菜单、角色菜单授权、唯一默认仓库所需种子；不使用 AutoMigrate。
- 商品与服务共用资料表，区分类型；参考价采用可空整数分，API 用十进制字符串表达，不使用 float。数量三位小数是后续单据约束，本轮不增加库存数量字段。
- 往来单位共用一份身份记录，用两个业务角色标记表达客户、供应商，可同时为真；开票资料为选填信息，不增加开票流程。
- 唯一逻辑仓库由数据库约束与种子共同保证，重复执行迁移不能重复创建。
- 新增、编辑、启停业务资料以及修改仓库必须与操作审计在同一事务内提交，写入或审计失败时整体回滚。
- 现有系统管理功能与示例页面保持原有边界，不复用示例数据充当业务档案。

### 验收与检查

- 可维护不同规格的硒鼓、打印机、内存、硬盘、整机及安装/维修服务；实物与服务可筛选，服务没有库存字段或出入库行为。
- 同一往来单位可同时具有两种身份；个人客户只需填写名称，分类与身份由页面默认或选择，其他业务资料可空。
- 编码自动生成或手工填写，重复编码被拒绝，同名不同规格可共存；价格空值、零值与两位小数准确往返。
- 新增、编辑、详情、分页、筛选、启停在前后端连通；停用资料保留，仍可查看、编辑、恢复。本轮尚无单据，后续新单据禁止选用停用资料的规则在单据阶段验证。
- 只存在一个默认仓库，名称与备注可修改；没有新增、删除、停用入口或接口。
- 菜单正确注册并授权，未登录访问接口被拒绝；已登录账号的访问范围以最终确认的权限规则为准。
- 关键验证覆盖重复编码（含并发写入）、输入校验、价格精度、双重业务角色、默认仓库唯一性、资料写入和审计的原子性，且在 PostgreSQL/SQLite 上验证。
- 运行 `task backend:check`、`task frontend:lint`、`task frontend:build`、`task db:check`；检查数据库测试入口的筛选表达式，保证本轮业务 contract 被实际执行。
- Swagger 必须由源注解重新生成；报告各项检查结果及任何未执行项。
