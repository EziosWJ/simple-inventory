# Phase 2：商品与服务、往来单位、单一逻辑仓库基础资料

## Problem Statement

经营者本人管理一家小型个体户，经营硒鼓、打印机、内存、硬盘、整机等商品，也可能提供安装、维修服务。上游多为同行，客户包括国企、事业单位、私企和个人；同一交易对方可能同时是客户与供应商。

系统目前只有认证、系统管理等基础能力，尚不能维护这些真实业务资料。经营者需要先建立准确、可查询、可持续维护的基础档案，为后续采购、销售、库存提供统一身份和计量口径。

## Solution

提供商品与服务、往来单位、仓库三个业务入口。不同规格的实物商品分别建档，服务项目单独区分且不产生库存；每项资料使用一个基本单位，并可维护人民币参考价。客户与供应商共用往来单位档案，同一档案可有两种身份。系统预置唯一逻辑仓库，只维护名称和备注。

商品与服务、往来单位支持手工新增、编辑、详情、分页筛选、停用与恢复；基础资料不提供删除。本轮沿用现有登录认证与菜单角色授权，业务写入与操作审计原子提交，PostgreSQL 与 SQLite 提供一致的可观察业务行为。

## User Stories

1. As an 个体户经营者, I want 建立硒鼓、打印机、内存、硬盘和整机档案, so that 后续采购与销售可以选择真实商品。
2. As an 个体户经营者, I want 将不同容量、型号和规格分别建档, so that 不同实物的库存与交易不会混淆。
3. As an 个体户经营者, I want 记录商品的名称、品牌、型号和规格, so that 能辨认同名商品。
4. As an 个体户经营者, I want 用普通分类名称整理资料, so that 能按业务类别查找商品而不维护复杂分类树。
5. As an 个体户经营者, I want 将整机作为可销售成品建档, so that 可以维护不同成品配置的资料。
6. As an 个体户经营者, I want 建立安装、维修等服务项目, so that 后续销售单可以选择服务。
7. As an 个体户经营者, I want 明确区分实物商品和服务项目, so that 服务不会被错误地纳入库存。
8. As an 个体户经营者, I want 为每个商品或服务设置一个基本单位, so that 后续填单有明确的数量口径。
9. As an 个体户经营者, I want 使用支、台、条、块、次或小时等单位, so that 实物与服务均可按实际业务计量。
10. As an 个体户经营者, I want 可选地记录参考采购价和参考销售价, so that 后续填单可以参考常用价格。
11. As an 个体户经营者, I want 人民币参考价精确保存到两位小数, so that 查询或再次编辑时价格不会漂移。
12. As an 个体户经营者, I want 区分未填写价格与零价格, so that 未定价不会被误解为免费。
13. As an 个体户经营者, I want 在编码留空时由系统生成唯一编码, so that 不需要自行编排每条资料的编号。
14. As an 个体户经营者, I want 手工填写或修改商品、往来单位编码, so that 能沿用已有编号或纠正录入错误。
15. As an 个体户经营者, I want 系统拒绝各自档案范围内的重复编码, so that 每个编码明确指向一份资料。
16. As an 个体户经营者, I want 名称相同的商品或交易对方可以分别建档, so that 不同规格或同名交易对方不会被强制合并。
17. As an 个体户经营者, I want 用关键词、类型、分类和启用状态查找商品与服务, so that 能快速找到所需资料。
18. As an 个体户经营者, I want 分页查看商品与服务并打开详情, so that 资料增加后仍能方便浏览。
19. As an 个体户经营者, I want 编辑商品类型、基本单位及其他资料, so that 初始录入错误可以纠正。
20. As an 个体户经营者, I want 将不再销售的商品或服务停用, so that 资料保留且后续新单据不再选择它。
21. As an 个体户经营者, I want 查看、编辑并重新启用停用资料, so that 业务恢复时可以继续使用同一档案。
22. As an 个体户经营者, I want 为单位和个人建立往来单位档案, so that 两类交易对方都可以管理。
23. As an 个体户经营者, I want 一份往来单位档案同时具有客户与供应商身份, so that 与同行双向交易时无需重复维护资料。
24. As an 个体户经营者, I want 往来单位至少具有一种业务身份, so that 每份档案都有明确用途。
25. As an 个体户经营者, I want 记录一个主要联系人、电话、地址和备注, so that 可以查找日常联络信息。
26. As an 个体户经营者, I want 对个人客户只输入名称即可建档, so that 临时个人交易不需要填写大量资料。
27. As an 个体户经营者, I want 可选地记录开票名称、税号、注册地址及电话、开户行和账号, so that 需要开票时能查到基础信息。
28. As an 个体户经营者, I want 按关键词、单位/个人分类、客户/供应商身份和启用状态筛选往来单位, so that 可以快速找到交易对方。
29. As an 个体户经营者, I want 分页查看往来单位并打开详情, so that 资料数量增加后仍便于查询。
30. As an 个体户经营者, I want 编辑往来单位的业务身份、联络与开票资料, so that 一份档案可以持续保持准确。
31. As an 个体户经营者, I want 停用和重新启用往来单位而不删除档案, so that 业务关系变化后仍保留资料。
32. As an 个体户经营者, I want 系统预置一个默认逻辑仓库, so that 后续库存有统一归属。
33. As an 个体户经营者, I want 修改唯一仓库的名称和备注, so that 名称符合我的业务习惯。
34. As an 个体户经营者, I want 新资料默认启用且只要求必要字段, so that 日常录入简单直接。
35. As an 个体户经营者, I want 无效或重复输入显示清晰错误, so that 能及时纠正资料且不会留下半成品记录。
36. As an 个体户经营者, I want 沿用已有登录与管理布局进入业务页面, so that 不需要新的账号或独立应用。
37. As an 个体户经营者, I want 未登录时业务接口拒绝访问, so that 资料只向已登录账号开放。
38. As an 个体户经营者, I want 成功的资料修改同时留下操作审计, so that 可以追踪资料维护行为。
39. As an 个体户经营者, I want 写入或审计失败时整次操作回滚, so that 收到失败结果时资料没有发生不完整变更。
40. As an 个体户经营者, I want 在 PostgreSQL 和 SQLite 上获得一致的资料维护行为, so that 可以按部署条件选择受支持数据库。

## Implementation Decisions

1. 本轮只实现 Phase 2 基础资料，不开始库存、采购或销售单据功能；不存在库存数量字段或服务出入库行为。
2. 新增 product、partner、warehouse 三个业务模块，按 Handler → Service → Repository 边界组织，依赖显式组装；Service 不依赖 Gin、GORM 或数据库方言，沿用 ADR-0004。
3. 实物商品与服务项目共用资料结构，通过类型区分；不同规格分别建档。资料包括编码、名称、类型、品牌、型号、规格、分类名称、基本单位、参考采购价、参考销售价、备注及启用状态。名称、类型、基本单位必填；编码可省略，其他业务字段选填。
4. 整机按可销售成品表达，不实现配置组合、配件消耗或组装过程。分类为普通文本，不引入独立分类树、品牌或规格管理模块；基本单位为单一单位，不做包装自动换算。
5. 参考价统一人民币，可空或为零，不得为负数，不接受超过两位小数。存储采用可空整数分，接口使用十进制字符串和空值；输入、校验与格式化避免 float，明确区分未定价和零价格，并检查存储范围溢出。
6. 数量允许三位小数是后续单据约束，本轮不引入数量计算或库存余额。参考价不等于实际成交价或库存成本。
7. 客户、供应商共用往来单位档案，沿用 ADR-0011。名称、单位/个人分类必填，以两个独立业务身份表达客户与供应商，至少一种为真；主要联系人、电话、地址、备注与开票资料均选填。
8. 开票资料包括开票名称、税号、注册地址、注册电话、开户行、账号；只存资料，不实现开票流程或真实性查询。个人客户表单默认个人分类与客户身份，可以只输入名称提交；编码由系统生成。
9. 商品与往来单位各自有编码唯一约束，编码允许手填或自动生成，可在本阶段编辑。编码统一大写并去除首尾空白，必填文本拒绝纯空白；名称允许重复。重复编码包含停用档案，不因停用释放编码。
10. 内部身份沿用数据库生成的数值 ID，不用业务编码作为关联主键；数据库约束兜底编码唯一性，并将并发冲突转换为可理解的业务错误。自动编码碰撞不得覆盖或合并已有记录。
11. 商品与往来单位默认启用，支持编辑、详情、停用、恢复，没有删除入口和接口。停用资料仍可查询、编辑、恢复；后续新单据不得选择停用资料，该选用规则留到单据阶段验证。
12. 本阶段允许纠正商品/服务类型、基本单位和业务编码。后续业务引用建立后，再明确类型、单位等字段的修改限制，本轮不虚构未实现的引用校验。
13. 唯一逻辑仓库由种子建立，默认名为“默认仓库”，只可修改必填名称与可选备注，没有新增、删除、停用能力；数据库约束保证最多一份仓库记录，重复迁移不得重复建立。
14. PostgreSQL 与 SQLite 使用逻辑版本锁步的 Goose schema 和 seed migration；不改写已执行迁移，不使用 AutoMigrate，API 启动不自动迁移或补种。正式数据库支持边界沿用 ADR-0010。
15. 每次成功新增、编辑、状态修改及仓库修改都与操作审计在同一 Repository 事务内完成；写入或审计失败整体回滚。审计通过已有 audit 模块，不新增通用事务框架，沿用 ADR-0006。
16. 新接口统一使用 `/api/v1`，保留既有兼容接口。商品：GET/POST `/api/v1/products`、GET/PUT `/api/v1/products/:id`、PUT `/api/v1/products/:id/status`；往来单位：GET/POST `/api/v1/partners`、GET/PUT `/api/v1/partners/:id`、PUT `/api/v1/partners/:id/status`；仓库：GET/PUT `/api/v1/warehouse`。
17. 状态接口设置明确目标状态，不用 toggle；重复设置同一状态后资料状态一致。API 沿用现有响应封装、分页与错误语义，不泄露底层数据库错误。
18. 分页参数为 page、pageSize，默认第一页、每页 10 条，上限 500；返回 records、total、page、pageSize。分页使用确定性排序，筛选条件参与总数统计。
19. 商品关键词覆盖编码、名称、品牌、型号、规格，另支持类型、分类、启用状态筛选；往来单位关键词覆盖编码、名称、联系人、电话，另支持单位/个人分类、客户或供应商身份、启用状态筛选。具有双重身份的往来单位在两种身份筛选中均可找到。
20. 前端复用已有设计系统、Standard List Page、列表状态管理、表格、表单弹窗与确认组件，新增三个真实业务入口。商品列表展示型号、规格、类型、单位和参考价，避免同名资料难以辨认；仓库为单份资料维护页面。
21. 沿用 JWT 登录认证与菜单角色授权，新增真实业务菜单并授权内置 ADMIN 角色。本轮不增加按操作权限编码校验：所有已登录账号均可调用业务接口，菜单隐藏不构成 API 授权限制；不使用 mock 权限工具作为真实授权。
22. 客户端与服务端均校验输入；表单显示字段错误并保留用户输入，成功后刷新相关列表或详情。价格表单和响应明确区分空值与零值。
23. 所有新增与修改 API 同步 Swagger 源注解，并重新生成文档产物；不手工修改 generated 文件。
24. 各纵向任务都交付所需的双库迁移、API、UI、菜单接入、审计、Swagger 和相应验证，不将基础设施拆成不能独立演示的横向任务。无需先做大范围重构。

## Testing Decisions

以下测试边界为待确认方案，确认后作为规格的正式测试要求。

1. 主测试边界使用现有应用 HTTP 路由连接真实数据库：通过公开请求及响应验证登录、参数校验、建档、详情、分页筛选、编辑、启停、仓库维护。使用同一套业务场景分别运行 PostgreSQL 与文件型 SQLite，不新增仅为测试服务的业务接口。
2. 好测试验证外部可观察行为，不断言私有函数、SQL 拼接、GORM 调用顺序或组件内部状态。主要覆盖成功行为、无效输入、边界值、编码冲突、并发提交和失败后资料是否改变。
3. 商品模块重点验证实物/服务区分、不同规格同名建档、金额空值与零值、两位小数精确往返、非法与溢出金额拒绝、编码规范化及唯一性、分页筛选、编辑和启停。价格解析与格式化若需要少量纯函数边界测试，只验证输入输出，不增设多层重复测试。
4. 往来单位模块验证单位/个人、双重身份、无身份拒绝、个人仅输入名称、可选开票信息、编码冲突、分页筛选、编辑及恢复；仓库模块验证唯一种子、迁移可重复执行、重启后保存的名称与备注仍在。
5. 审计原子性沿用现有 RBAC 写入与审计同事务、SQLite 业务与审计回滚的集成测试先例。需要时直接观察提交后的数据库记录或注入审计失败，以确认业务与审计同时存在或同时不存在；不为方便测试而引入通用事务抽象。
6. UI 按用户路径验证“进入菜单 → 新建 → 查询/详情 → 编辑 → 停用 → 恢复”和“查看/修改唯一仓库”，覆盖表单错误、价格空/零、同名规格展示、筛选分页。现有前端没有为本需求承诺新的浏览器测试框架；可采用实际页面操作验收，并执行 lint/build。
7. 每次数据库改动均在隔离 PostgreSQL 与文件型 SQLite 验证空库迁移、增量升级、schema/seed 版本一致、约束及审计回滚。修正或命名集成测试入口，确保新增 contract 实际被现有检查命令执行；自动化测试不连接实际部署数据库。
8. 完成后执行后端 tests+vet、前端 lint/build、双库集成检查，核对 Swagger 已重新生成。汇报通过、失败和未执行项，不将未运行或被筛选掉的测试视为通过。

## Out of Scope

- 当前库存、库存流水、库存调整与实际数量计算。
- 采购入库、销售出库、过账、反向流水及单据引用后的编辑限制。
- 多仓、按实物地点拆分、仓库新增删除或停用。
- 逐台序列号、销售去向、保修追踪、组装 BOM、配件消耗及复杂规格组合。
- 多单位和包装自动换算、复杂分类树、独立品牌管理。
- 实际成交价、库存成本核算、财务总账、应收应付、收付款和开票流程。
- 批量导入导出、报表、打印、商品图片或附件管理。
- 删除基础资料、批量维护及新的细粒度 API 权限系统。
- 微服务、通用 CRUD 框架、通用事务协调器、新的浏览器自动化框架及 MySQL 正式支持。

## Further Notes

业务范围、字段、校验、编码维护、启停、仓库与权限规则已通过访谈确认。本轮工作为生成规格与任务，不实现功能。

当前规格为发布草案；测试边界及纵向任务拆分确认后，将创建 GitHub 规格 issue 与五个任务 issue，统一标记 ready-for-agent。任务按真实依赖发布，规格 issue 作为来源，不关闭或修改已有父 issue。

未来阶段接入库存或单据时，需要再次讨论 SN、已引用类型与单位的修改限制、服务与实物的单据差异、库存精度与成交价格；本规格不预先实现这些能力。
