# 往来管理使用体验需求讨论

## 讨论起点

- 用户提出进一步优化往来管理的使用体验，以「往来余额」为首个例子；现有功能已实现，但使用体验不友好。
- 本轮按 grill-with-docs 访谈并记录结论。Q1～Q9 已确认，用户随后调用 to-spec，确认测试边界并授权发布与实施；正式规格已发布为 [GitHub #64](https://github.com/EziosWJ/simple-inventory/issues/64)。

## 已核对的现状

- 产品面向共同经营小型店铺的两名经营者，主要使用电脑浏览器。
- 往来余额页按往来单位和客户／供应商方向展示，一单位可有两行；当前显示有符号金额、状态、来源记录数及行内操作。
- 筛选包含往来单位与方向。行内可进入明细，正余额进入收款／付款，负余额进入退款；期初录入位于页头。
- 当前页面路径与拆分约定见 [Phase 4 往来页面拆分](phase-4-partner-pages.md)，此前查账体验验收要求见 [Phase 5 T07](phase-5-tickets/07-partner-query.md)。
- 现状依据：`web/src/pages/business/partner-balances.tsx`。本轮尚未进行浏览器实际操作，代码现状不等同于用户体验结论。

## 既有领域边界

- 同一单位的客户与供应商余额分别保留，不自动抵扣。
- 收付款按单位总余额记录，不分配到具体采购或销售单。
- 正余额表达欠款，负余额表达待退款；「净结清」不能据此推断某张单据已结清。
- 本轮沿用上述领域边界，采用当前余额概览与金额排名，未增加逐单核销或历史趋势需求。

## 第一轮已确认

- Q1：用户希望打开页面就能按顺序看到往来数据，或通过图形化展示一眼获取决策所需数据，而不是以逐个选择客户或供应商查询为主要使用方式。排序与可视化形式见 Q5、Q6。
- Q2：先优化往来余额及相邻完整链路：查余额 → 看明细 → 登记收付款 → 返回核对，再扩展其他页面。
- Q3：默认提供全店待处理事项，展示待收款、待付款、待退款，保留快速搜索单位；同一单位的应收、应付分别计算。

## 补充事实与体验假设

- 代码中未选单位时已经查询跨单位余额，但默认包含尚无记录和净结清方向，按单位 ID 与方向排序；没有按待处理状态筛选、欠款金额排序或跨页金额汇总。用户描述的是使用体验，不能据此认定现有接口只能查一个单位。
- 收付款／退款入口虽然携带单位和方向，资金页仍采用最多 500 条单位的原生下拉；金额缺少全额快捷入口，超额或格式错误主要通过禁用按钮表达，完成后的来源返回入口不直接。
- 余额列表来源为 `server/internal/receivable/opening.go`；相邻资金页为 `web/src/pages/business/partner-funds.tsx`。以上均为代码核对，尚未进行本轮浏览器验收。

## 第二轮已确认

- Q4：页面顶部展示四项全店汇总，每项包含总金额与单位数量：待收款（客户欠店铺）、待付款（店铺欠供应商）、待退客户（店铺需要退给客户）、待收供应商退款（供应商需要退给店铺）。统计不受分页影响，四项不合并为净额。
- Q5：点击汇总查看对应列表，默认进入待收款，按金额从大到小排列；结清和无记录方向通过「全部」查看。
- Q6：提供欠款金额前十名的横向条形图，可切换客户欠款与供应商欠款，点击可进入明细；同时保留完整可操作列表。本轮采用当前欠款分布，未提出历史趋势需求。

## 第三轮已确认

- Q7 已确认：顶部四项汇总与前十名图表始终展示全店情况，搜索只筛选下方列表，明确标注统计范围；从明细返回保留分组、搜索和页码。
- Q8 已确认：四项正式名称为「客户应收」「供应商应付」「应退客户款」「应收供应商退款」，替代前两轮暂用的待收／待付名称。页面注明「当前未结余额」；待处理列表用具体业务名称和正数金额表达，明细账保留有符号余额。同一单位两个方向分别展示。按钮继续使用「收款」「付款」「向客户退款」「收供应商退款」。
- Q9 已确认：从余额进入时带入单位与收款／付款／退款类型，提供「填入全额」按钮并允许部分金额；超额及格式错误就地说明。保存成功显示本次金额与最新余额，提供「返回往来余额」「继续登记」两个入口；返回后刷新数据并保留查询条件。

## 收口方案

### 页面结构

1. 顶部为「全店当前未结余额」四项概览，每项展示金额与有对应余额的单位数量；金额按当前余额分类求和，不合并两个方向，也不受列表分页或搜索影响。
2. 中部为全店客户应收／供应商应付前十名横向条形图，支持切换方向并进入对应单位明细。
3. 下方为可搜索、分页和操作的余额列表。默认客户应收，按金额从大到小排列；点击概览切换对应分类，另有「全部」入口查询净结清及无记录方向。
4. 搜索仅影响列表，概览与图表明确标注全店范围；列表保留进入明细和办理款项的入口。
5. 资金页带入单位与办理类型，金额由用户填写或点击「填入全额」；保存后显示回执、最新余额及返回／继续登记入口。

### 验收场景

- 无需选择单位，打开页面即可看到四项概览、金额排名及客户应收列表；超过一页的数据仍全部纳入概览与排名。
- 同一单位既是客户又是供应商时，两个方向分别纳入对应分类，不相减；退款金额以正数显示，办理退款的资金方向清楚。
- 图表不足十个单位时展示实际数量；没有对应欠款时显示明确空状态。查询中和失败时不把未知余额显示为已结清。
- 点击概览进入对应分类；搜索只改变列表；从图表或列表进入明细后返回，保留原分组、搜索及页码。
- 可办理部分或全额款项；非法金额、超额及最新余额变化导致的拒绝明确说明，失败保留输入；保存成功后返回列表会读取最新数据。
- 当前某方向余额归零后，不再出现在该待处理分类；仍可在「全部」及明细中追溯历史，不推断单张采购／销售单已结清。

### 实施与验证约束

- 统计、分类与排序须覆盖全量符合条件数据，不能仅对当前分页求和或排序；接口是否新增或扩展在实施时依据现有结构决定。
- 保留业务金额语义与服务端校验；资金修改继续满足审计和事务一致性。
- 实施后按变更范围运行最小相关检查和项目门禁；后端或数据库相关变更执行双库定向验证及 `task db:check`，前端执行 lint/build。REST API 如有变更同步源注解并运行 `task api:docs`。
- 访谈阶段仅修改讨论文档与领域词汇表；授权后的实施与真实验收结果另记交付文档。
