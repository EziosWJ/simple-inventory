# Phase 4：采购、销售、退货、往来结算与单据打印

状态：已确认。Q1～Q42 的访谈已完成，用户已授权按 to-spec → to-tickets 直接发布，测试边界和完整范围已确认。

**GitHub 规格 issue：** [#14](https://github.com/EziosWJ/simple-inventory/issues/14) · `ready-for-agent`。

## Problem Statement

经营者已能维护商品、服务和往来单位，也能通过库存调整建立库存，但还不能记录实际采购和销售、日常赊账、分次收付款或退货退款。供应商多为同行，同一往来单位可能既是客户又是供应商，也存在供应商直送客户的交易。送货后需要客户在纸质单据上签收，并按期间核对欠款。用库存调整替代采购、销售会丢失成交价格、往来金额和业务来源；仅保存当前欠款又无法解释变化或纠正录错记录。

## Solution

提供采购入库、销售出库、采购退货、销售退货和往来结算业务入口，采购与销售共同规划、按采购 → 销售分批实现。一张采购/销售单记录一次收货/交付，草稿可编辑，整单过账后库存和往来金额一起生效，取消保留原记录并追加反向变动。

赊账按往来单位的客户/供应商两个方向分别计算总余额。期初欠款、收付款、退款和冲销可追溯，不逐单分配款项，不自动抵扣应收应付。退货先减总欠款，超出部分形成待退款；普通预收预付不在本阶段范围内。支持分次部分实物退货，使用原成交价并准确处理金额尾差。

供应商直送仍用两张关联单据，先采购入库再销售出库，分别过账；直送退货先销售退货再采购退货。提供 A4 送货单和期间对账单，销售历史资料包含空值也保持不变，送货单支持金额显隐和纸质签收。库存成本、毛利、SN 和服务退费暂缓。

## Implementation Decisions

### 1. 业务边界与模块

采用现有模块化单体和 Handler → Service → Repository。新增采购、销售及往来结算业务能力，扩展现有库存与商品引用锁定能力；依赖显式组装，Service 不依赖 Gin、GORM 或数据库方言。业务写入通过同一个数据库事务完成，不引入消息总线、异步余额投影、通用单据平台或大范围重构。

ADR-0011 的统一往来单位、ADR-0012 的商品历史身份锁定、ADR-0013 的按往来总余额结算继续适用。唯一逻辑仓库不表达实际存货地点。订单、待履约计划及部分过账不在首版交付中，分次收货/交付分别记录实际单据。

### 2. 单据内容与状态

采购/销售及退货单使用 DRAFT → POSTED / CANCELLED 状态流。至少一行；系统生成唯一且不可修改的单号，保存后不删除。草稿新建、编辑与取消不改变库存或往来金额，编辑/过账/取消携带核对版本；终态不可编辑或重新过账。取消必填原因，展示整单影响，保留创建、过账、取消的实际操作人及时间，重复请求或并发仅产生一次效果。

采购/销售记录往来单位内部 ID、业务日期、商品内部 ID 与稳定明细 ID、用户确认的类型和单位、正数量、非负成交单价及说明。同商品允许多行、不同价格，库存校验必须按商品汇总；退货额度按原明细维护。不得把调整单的“同商品只能出现一次”规则错误套用到采购/销售。

采购只接受启用实物商品及启用供应商，销售接受启用实物/服务及启用客户。创建、编辑与过账重新验证资料；类型、单位变化必须让用户重新确认，不静默换算。停用或业务身份不再符合的新单及草稿过账拒绝；历史退货、结算、退款和冲销仍可处理，但其他状态/额度/库存约束继续适用。

### 3. 数量与成交金额

数量使用最多三位小数的准确十进制字符串，持久化可用整数千分单位；人民币单价及金额使用两位小数，持久化可用整数分。禁止 float 运算。数量必须为正，单价可为零，负单价、超精度、无效输入、乘法/求和/取反溢出拒绝；中间乘法必须采用安全的整数或 decimal 运算。

行金额为数量乘单价四舍五入到分，单据金额为行金额之和。零价实物正常变动库存，纯服务和零价服务不生成库存流水；零金额单据允许生效，但不伪造非零资金记录。商品参考价仅供填单参考，实际成交以已保存单据为准，不单独计算折扣、运费或税额。

### 4. 库存与事务

采购过账增加实物库存、销售过账减少实物库存；采购退货减少库存、销售退货增加库存，取消产生对应反向变动。库存按商品合计校验、记录前后余额及稳定来源关联，保留各业务明细的数量、价格与来源；不要求同商品分行必须对应多条库存流水，允许按商品汇总但须完整追溯到来源单据/明细集合。

库存余额、全部库存流水、往来金额流水与余额、单据状态、退货累计额度及操作审计同事务提交。任一库存不足、金额超范围、来源无效、状态竞争或审计写入失败整单回滚。并发首次入库不重复余额行，跨单并发扣减不超扣；重复过账/取消/冲销不重复记账。事务内协调商品资料修改与首次产生库存流水，类型/基本单位永久锁定，归零或取消不解锁。

### 5. 多来源库存的兼容接入

现有库存流水只关联调整单且保存调整专属原因。扩展时保留旧调整 ID、原明细关联、ORIGINAL/REVERSAL 语义和历史查询行为，新增可识别采购、销售及退货的业务来源类型、单号、来源标识与冲销关联；不得把采购/销售伪装成库存调整或改写旧流水。

新增来源约束、唯一性及必要索引通过增量 Goose 迁移完成，并验证 Phase 3 已有数据可继续读取。数据库专属锁、SQL 和约束局限于持久化层。商品引用锁必须覆盖新来源，当前库存读取同一真实余额，服务不进入库存。每个写入任务交付自己来源的读取与详情追溯，完整多来源筛选在后续任务贯通。

### 6. 历史快照与时间

商品描述过账冻结，含当时为空的型号/规格，不能回退到当前档案。销售还冻结客户名称、送货联系人/电话/地址与经营者抬头/电话/地址；草稿读取已保存内容，新单默认带入档案，允许修改本次送货信息。旧送货单重印使用冻结快照，草稿打印标记未过账。

业务日期与实际录入/生效时间分开记录。库存及往来明细/期间余额按实际生效时间，跨期补录、取消和冲销计入实际发生期间，不修改原期间记录；同时展示业务日期。时间 API 使用 RFC3339、统一 UTC 瞬间，期间筛选下界包含、上界不包含；前端整日筛选按本地日界转换，业务日期使用日期值不发生时区漂移。按生效时间与稳定 ID 排序。

### 7. 往来余额与不可变金额记录

客户/供应商方向分别维护签名金额余额和不可变流水，不自动抵扣，不逐单核销，不显示推断的单据未结/结清状态。正余额是该方向尚欠款，负余额是该方向待退款；零余额是该方向净结清。

| 生效业务 | 该方向余额变化 |
| --- | --- |
| 期初应收/应付 | 增加金额 |
| 销售/采购过账 | 增加单据金额 |
| 销售/采购退货 | 减少退货金额 |
| 客户收款/向供应商付款 | 减少实际金额 |
| 向客户退款/收到供应商退款 | 增加实际金额 |
| 对应业务取消或资金/期初冲销 | 原金额的相反变化 |

余额等于该方向所有已提交金额流水累计，记录变动前后余额、实际执行人、生效时间、业务日期、来源与反向关联。退货先减总欠款，超出部分待退款；销售欠 400 退 500 → 待退款 100。历史资料停用不阻断该方向旧余额结算，收付款不强制当前档案仍有相应角色，但不为无历史余额资料制造新交易。

### 8. 期初、普通收付款与退款

期初可分次录入正金额、方向和必填说明，确认保存即生效，不补造历史交易/库存。普通收款/付款要求当前该方向余额为正且金额为正、不超过欠款；退款要求当前余额为负且正退款额不超过待退款绝对值。实际退款与普通预收预付区分，不用不支持预付来拒绝业务退货/取消形成的待退款。

收付款、退款确认前展示对象、金额、方向及余额变化，保存即生效、之后不编辑对象或金额。记录现金/微信/支付宝/银行转账/其他，流水号和备注选填；重复提交防重。冲销必填原因、保留原记录、关联原资金记录，且同一生效记录最多被冲销一次；再次纠正重录新记录。期初冲销会形成无依据待退款则拒绝；合法原交易取消或退款冲销产生的余额按已有业务依据处理，不套用普通付款的录入上限。

### 9. 真实退货与金额尾差

一张退货单对应一张原 POSTED 采购/销售单，可以选择多个原实物明细，但不跨原单、不退服务。数量为正，累计仍生效退货数量不能超过原明细数量，不能通过重复原明细或并发提交绕过额度；同商品不同价格的额度不得互换。使用原类型/单位/价格/商品快照，不使用当前档案或参考价重新定价。

本次退货金额＝累计仍生效退货数量乘原单价四舍五入到分的金额－此前仍生效退货金额。全部退完恰好等于原行金额；极小数量零金额仍保留实物变动。单据取消仅允许每一原明细上最新仍生效的退货，较早记录须先逆序处理后续记录；恢复数量额度并反向记回取消单原金额，不重算其他历史。原单有生效退货时不能取消。

### 10. 取消与实际资金的关系

取消交易或退货保留真实收付款/退款记录，不级联删改资金记录。取消已收款销售 1000 → 待退款 1000；可以退款或新建正确销售抵减。销售退货 200 已实际退款后取消退货 → 客户重新欠 200；退款录错须另行冲销退款。采购侧对称。任何反向库存结果为负则整单拒绝。对已取消历史仍保留来源、全部原明细和过账/取消记录。

### 11. 直送

每张直送采购最多关联一张未取消的销售单，旧已取消关联保留。一张销售对应一张直送采购，按实物商品汇总 ID/数量一致，采购和销售价格/行数可不同，销售可加服务费。销售过账在事务内核对关联采购 POSTED、关联唯一性及汇总一致；先采购后销售分别确认过账，允许中间暂时有库存，不提供同时过账的一键入口。

取消采购前先取消关联未取消销售，原单有生效退货先处理退货。直送退货仍先销售退货后采购退货，各自关联原单/原明细、受自身库存/额度/金额限制；界面展示两边来源与状态，不增加自动退款或两单部分生效的联合操作。

### 12. 查询与打印

真实采购、销售、退货菜单交付分页列表、详情、状态/单号/往来单位/业务日期等必要查询，商品筛选多行单不得重复计数。分页沿用 records/total/page/pageSize，默认 1/10、上限 500，结果/总数同过滤、排序稳定。错误保留输入并解释资料停用、数量不足、额度变化和版本冲突。明细与动作展示真实执行人，创建人不替代过账/收款人。

往来余额列表按方向查询，包含欠款、待退款、净零及停用历史；明细可按单位/方向/生效时间查期初、采购/销售、退货、收付款、退款与冲销，每条显示来源及前后余额。期间对账打印包含期间开始之前的累计余额、期间流水与期末余额，不能由当前余额倒推，不因分页遗漏记录，未来冲销不改写旧期间。

经营者名称/电话/地址统一维护并审计，新单带入，销售过账冻结；无需新建公司/多组织模型。送货单和对账单 A4 纵向、长单自动分页、单号/标识及页码、末页合计，送货单签收栏。送货金额隐藏同时隐藏单价、行金额及金额合计，不只隐藏某一列。打印内容来自已保存单据或完整期间数据，不能直接打印当前列表的一页或仅依赖可变页面 DOM 作为数据来源。

### 13. API、迁移与权限

新增业务 API 使用 /api/v1，沿用 JWT、响应封装和错误语义。建议单据资源分别为 purchases、sales、purchase-returns、sale-returns，提供分页/详情/草稿创建编辑及 post/cancel；往来资源提供 balances/entries、opening-records、settlements 及对应 reversal，经营者打印资料为单份资源。最终命名可按现有路由惯例调整，不改变公开行为；不提供直接覆盖余额或删除流水接口。

独立采购/销售/退货单与明细、来源关联、往来余额/流水、资金记录及经营者打印资料通过双库同步增量 schema/seed 迁移落地，不改旧版本、不使用 AutoMigrate、API 不自动迁移或补种。数据结构以承载已确认规则为准，不提前抽象通用财务账本。所有 REST 源注解与 Swagger 重新生成同步。

所有已登录账号可调用业务接口、维护任意业务记录，真实菜单按角色授权且授予内置 ADMIN；不增加单据所有权/岗位授权、不将 mock 显隐作为 API 授权。新增成功业务维护和审计同事务，拒绝未登录请求。

### 14. 当前实现事实与前置收尾

当前只实现商品/往来单位/仓库、调整、库存余额/流水；尚无采购、销售、往来结算、正式打印。库存流水的调整专属关联和原因不能直接承担新来源，商品锁定也须继续覆盖所有库存历史。先通过真实期初欠款建立可验收的往来写入路径，再接入采购/销售，避免横向空基础设施任务。

Phase 3 #10 的空型号/规格快照缺口及 #13 的来源详情验收未完成，#7 仍开放。新业务首次接入库存必须先完成 #10/#13 收尾并验证旧路径，复用现有 issue、不重复发布修复任务、不把开放状态视为已解决。独立往来期初或经营者打印资料维护不消费库存，可先行交付；不要求横向大重构。

## Testing Decisions

测试边界已在 Q42 整体确认。本次用户进一步授权直接发布，无需再采访或审批。

1. 主要测试边界为现有认证 HTTP 路由连接真实数据库，同一业务场景运行隔离 PostgreSQL 与文件型 SQLite；优先复用 Phase 2 基础资料、Phase 3 库存与审计回滚的公开 HTTP contract，不增加仅为测试使用的业务入口。
2. 好测试验证公开请求/响应、已提交数量/金额/来源/状态、失败后是否保持原数据；不绑定私有函数、SQL 拼接、ORM 调用顺序或 UI 内部状态。少量数量/金额/累计取整纯函数测试只覆盖难以直观看出的边界，不叠加镜像多层测试。
3. 采购/销售：草稿不生效、版本冲突、角色/停用校验、同商品分行汇总、零价赠品、三位数量/两位单价、乘加溢出、混合/纯服务、整单库存不足、重复与并发、审计/库存/金额写入失败回滚、商品身份永久锁定、描述空值快照。
4. 退货：原明细额度、不同价格分行、分次/并发不超退、累计取整与零金额、全部退完原金额、逆序取消及额度恢复、多行一项不满足全单拒绝、服务退费拒绝、停用历史处理、取消原单时生效退货阻塞、已退款取消后新欠款及原资金保留。
5. 往来：双方向不抵扣、期初分次与冲销、部分收付款、普通付款/退款上限、并发超额拒绝、同一记录最多一次冲销、退货先抵欠款、待退款被新交易抵减、余额等于原始与反向金额流水之和、实际操作人及来源追溯。
6. 直送：两单按商品汇总一致、行数/价格不同、服务附加、采购未过账拒绝销售、关联唯一性与并发、取消顺序、关联历史保留、先销售退货再采购退货。失败时不误报两张单都已生效。
7. 查询/时间/打印：稳定排序与分页总数、多行筛选去重、本地日期/UTC 半开范围、历史期间期初/期末累计、跨期补录冲销不重写旧期间、改名/停用/归零历史来源、金额显隐、草稿水印、冻结地址抬头、多页和末页合计、打印不遗漏超过当前页的记录。
8. 双库验证空库、从 Phase 3 增量升级、schema/seed 逻辑版本、旧库存数据读取、来源/唯一性约束与审计回滚。新增 contract 名含 Postgres 或 SQLite，确保被现有数据库门禁和 CI 选中；PostgreSQL 依赖 Docker，实际跳过须如实报告。
9. 真实浏览器按采购→销售→分次结算→部分退货→退款→冲销演示，另覆盖直送、退货取消后欠款、期初录入、库存/往来来源追溯、纸面送货签收和对账多页打印。复用现有浏览器工具和 lint/build，不承诺新的浏览器测试框架。
10. 各实现任务执行相关后端 tests/vet、前端 lint/build 和双库 contract；整阶段执行 task check 与 task db:check，记录通过、失败、跳过和未执行项。此次仅生成规格/任务，不宣称实现或运行其验收测试。

### Code Review 补充验收场景（2026-10-02）

以下场景把本规格已确认的行为具体化，用于 Phase 4 已交付能力的修复回归；不新增业务范围或改变既有规则。对应修复任务见[后续修复任务索引](phase-4-tickets/README.md#review-follow-ups)。

11. **退货草稿行对应：** 原采购/销售单有 A、B 两条明细，退货草稿只包含 B。编辑时数量只能显示在 B；修改 B 不得改变 A，保存后仍只关联 B 的稳定原明细 ID。采购和销售分别验证。
12. **商品单位重新确认：** 已保存草稿中的单位与当前商品档案不同时，编辑保存不得静默替换或换算数量。界面须明确要求用户确认新类型/单位，确认前仍保留草稿原值。采购和销售分别验证。
13. **销售业务日期与送货空值：** Asia/Shanghai 当地日期 00:15 新建销售草稿，默认业务日期为当天；销售单明确清空档案联系人、电话或地址后，保存、读取、过账和重印均保留空值。省略字段的新单仍按既有规则默认取档案资料。
14. **直送退货先后：** 直送采购和关联销售均已过账、另有库存可供退回、尚无关联销售退货时，直送采购退货过账必须拒绝，且单据、库存与往来保持不变。先过账关联销售退货后，再分别按采购退货自身的库存和原单额度规则处理采购退货；不增加自动联合过账。
15. **退货历史可读与执行人：** 已过账销售退货在列表和详情中显示实际过账人及时间。采购、销售退货经历全部退回、取消、再次退回后，原取消单详情和分页列表仍可读；取消单不计入当前生效退货额度或金额。
16. **SQLite 繁忙响应：** SQLite 写锁等待耗尽时，新增业务 API 按统一错误响应返回 HTTP 503，事务回滚，不返回通用 500 或部分成功状态。

## Out of Scope

- 负库存、历史库存倒签/重算、修改或删除历史流水、联合过账直送两单的一键操作。
- 独立折扣/运费/税额计算、Excel 导出、支付凭证附件、电子签名/签收照片上传。

- 本次发布流程中的业务功能实现、部署或自动关闭 Phase 3 未完成 issue。
