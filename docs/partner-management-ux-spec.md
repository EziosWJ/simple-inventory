# 往来余额：全店概览、欠款排名与款项办理体验

已发布为 [GitHub #64](https://github.com/EziosWJ/simple-inventory/issues/64)，标记 ready-for-agent；产品决策与测试边界均已确认，用户已授权本地实施。

## Problem Statement

经营者打开往来余额后，希望直接了解全店当前欠款和退款情况，判断应优先向谁收款、向谁付款，以及资金主要集中在哪些单位。现有页面虽然已有跨单位余额列表，但默认包含结清和无记录方向，按单位编号排列，没有全店金额汇总及欠款排名，使用时容易退回逐个选择客户或供应商查询的方式。

从余额进入款项办理后，金额填写、校验解释及完成后的返回路径也不够直接，经营者难以顺畅完成「查余额 → 看明细 → 登记款项 → 返回核对」。

## Solution

将往来余额组织为全店概览、欠款排名和可操作列表。顶部展示「客户应收」「供应商应付」「应退客户款」「应收供应商退款」四项当前未结余额及单位数量；中部展示可切换客户与供应商方向的欠款金额前十名横向条形图；下方默认展示客户应收，按金额从大到小排列，支持切换分类、搜索、分页、查明细和办理款项。

全店概览和图表不受列表搜索与分页影响，明确标注范围。办理款项时带入单位和类型，支持填入全额或录入部分金额，解释校验错误；保存成功后展示回执和最新余额，返回时保留查询条件并刷新。

## User Stories

1. 作为经营者，我希望无需先选择单位就能看到全店往来情况，以便打开页面即可判断待处理事项。
2. 作为经营者，我希望看到客户应收总额，以便知道客户当前还欠店铺多少钱。
3. 作为经营者，我希望看到供应商应付总额，以便知道店铺当前还欠供应商多少钱。
4. 作为经营者，我希望看到应退客户款总额，以便安排向客户退款。
5. 作为经营者，我希望看到应收供应商退款总额，以便跟进供应商应退回的款项。
6. 作为经营者，我希望每项概览显示对应单位数量，以便了解待处理对象规模。
7. 作为经营者，我希望概览覆盖全店而不是当前分页，以便依据完整金额作出判断。
8. 作为经营者，我希望看到「当前未结余额」说明，以便区分剩余欠款与累计采购、销售金额。
9. 作为经营者，我希望同一单位的客户与供应商方向分别保留，以便准确了解两个方向的款项。
10. 作为经营者，我希望应收、应付和退款不合并成一个净额，以便分别安排收付事项。
11. 作为经营者，我希望看到客户应收前十名条形图，以便看出客户欠款集中在哪些单位。
12. 作为经营者，我希望切换到供应商应付前十名，以便看出主要付款对象。
13. 作为经营者，我希望排名覆盖全店，以便不会遗漏列表其他页的大额欠款。
14. 作为经营者，我希望图表展示单位名称和金额，以便直接理解排名。
15. 作为经营者，我希望点击图表进入该单位正确方向的明细，以便核对欠款来源。
16. 作为经营者，我希望不足十个单位时看到实际数量，以便图表准确表达当前情况。
17. 作为经营者，我希望没有对应欠款时看到明确空状态，以便知道该方向当前无待处理欠款。
18. 作为经营者，我希望默认列表展示客户应收并按金额降序排列，以便优先查看金额影响最大的客户。
19. 作为经营者，我希望点击概览切换对应分类，以便快速查看应付款或退款对象。
20. 作为经营者，我希望通过「全部」查看结清和无记录方向，以便查询完整往来档案情况。
21. 作为经营者，我希望通过已有往来搜索找到指定单位，以便从全店概览转到具体对象查账。
22. 作为经营者，我希望搜索只影响列表且统计范围明确，以便不会把搜索结果误认为全店金额。
23. 作为经营者，我希望历史停用或身份变化单位的未结余额仍可查询，以便不会漏掉历史欠款。
24. 作为经营者，我希望待处理金额用业务名称与正数表达，以便不用根据负号判断退款方向。
25. 作为经营者，我希望明细账继续保留有符号余额和来源记录，以便核对原有往来变动。
26. 作为经营者，我希望从列表进入正确单位与方向的明细，以便减少重复选择。
27. 作为经营者，我希望从明细返回时保留分组、搜索和页码，以便继续此前的查账任务。
28. 作为经营者，我希望从余额进入款项办理时带入单位与办理类型，以便减少重复录入和方向错误。
29. 作为经营者，我希望点击「填入全额」填写当前可办理金额，以便快速完成全额收付款或退款。
30. 作为经营者，我希望也能登记部分金额，以便记录实际发生的款项。
31. 作为经营者，我希望格式错误和超额有明确解释，以便知道如何修改输入。
32. 作为经营者，我希望余额加载中与余额为零有不同反馈，以便不会误以为欠款已经结清。
33. 作为经营者，我希望余额发生变化导致办理失败时保留输入并说明原因，以便重新核对后办理。
34. 作为经营者，我希望成功后看到本次金额与最新余额，以便确认办理结果。
35. 作为经营者，我希望成功后可以返回余额或继续登记，以便按当前任务选择下一步。
36. 作为经营者，我希望返回余额后查询条件保留且数据刷新，以便确认处理后的结果。
37. 作为经营者，我希望余额归零后退出对应待处理分类但历史仍可查，以便兼顾日常办理与追溯。
38. 作为经营者，我希望查询失败有明确错误和重试入口，以便恢复查询而不误判金额。
39. 作为共同经营者，我希望重复提交和多人操作仍遵守现有金额规则，以便不重复记账或超额办理。
40. 作为经营者，我希望已有记录附件、冲销、来源追溯和对账打印继续可用，以便查账与处理凭证的任务保持完整。

## Implementation Decisions

- 改造往来余额查询与展示、收付款和退款表单、相关导航与成功反馈；沿用现有往来业务模块、往来搜索和通用页面组件。期初、附件、明细及打印的既有业务能力保持可用。
- 正式概览名称为「客户应收」「供应商应付」「应退客户款」「应收供应商退款」，统一解释为当前未结余额；操作按钮使用「收款」「付款」「向客户退款」「收供应商退款」。
- 客户方向正余额计入客户应收，供应商方向正余额计入供应商应付；客户方向负余额绝对值计入应退客户款，供应商方向负余额绝对值计入应收供应商退款。零余额和无记录方向不计入四项待处理金额或单位数量。
- 每项单位数量按该分类的往来单位统计；同一单位允许出现在不同方向分类，不自动抵扣，不计算两个方向合并净额。停用或身份变化对象的历史未结余额继续纳入对应统计。
- 概览覆盖全店；图表覆盖全店对应方向的正余额，按金额从大到小取前十个单位，显示名称及金额，点击进入该单位该方向明细。不足十个展示实际数量，无数据明确说明。
- 分页列表默认客户应收，按当前金额降序；四项概览分别进入对应分类，另有「全部」入口保留结清及无记录方向查询。退款分类按正数待退款金额表达和排序。相同金额采用稳定次序，具体次序由实施者选择，保证翻页稳定。
- 沿用既有往来搜索能力；搜索只影响列表，概览与图表明确标注全店范围。当前分组、搜索和页码通过既有导航机制保留，明细及款项办理返回后恢复上下文。
- 待处理列表用分类名称与正数金额表达；明细账和既有账务契约保持原有有符号余额，不把单位净结清推断为某张业务单据结清。
- 全量分类、汇总、数量、排名和排序在服务端查询边界保证准确；不得只用当前分页计算总额、前十名或排序。可以扩展现有公开查询或新增兼容查询，具体接口命名和响应结构由实施者确定，保留既有调用兼容性。
- 金额继续采用项目现有定点精度与人民币分口径，不能通过浮点计算改变金额；服务端聚合与排序满足 PostgreSQL、SQLite 一致性，数据库差异局部化。
- 从余额进入收付款／退款时带入单位、方向与办理类型；金额初始仍由用户填写，提供「填入全额」快捷操作，允许部分金额。全额依据最新可办理余额，保存仍以服务端最新余额校验为准。
- 金额格式和超额错误就地解释；加载、无可办理余额、查询失败明确区分，不能在加载中以零余额误导。提交失败保留输入并说明原因，成功显示本次金额、最新余额及「返回往来余额」「继续登记」。
- 返回余额时刷新相关概览、图表和列表，并保留查询上下文。已结清方向自然退出相应待处理分类，历史仍可在全部及明细查询。
- 沿用现有总余额结算、权限、幂等、审计及事务规则；收付款、退款金额不得跨越允许范围，查询体验优化不改变业务生效方式。
- 保持 Handler → Service → Repository 边界，Service 不依赖 HTTP 框架或具体数据库；本次没有已确认的新业务表需求。如实施确需 Schema 变更，使用双库同步 Goose migration，不使用 AutoMigrate。
- 修改公开 REST API 时同步源注解，使用项目固定命令生成并审查 Swagger。测试、页面布局和查询结构的具体组织由实施者在上述外部行为约束内确定。

## Testing Decisions

- **用户已确认的测试边界**：以现有真实浏览器与公开 API 链路作为用户体验主验收入口；复用双库公开 HTTP 集成契约补充全量统计、分类、排序和资金规则。不新增测试专用业务接口。
- 好的测试验证可观察结果：用户看到的金额、分类、排序与空状态，导航后单位／方向及返回条件，提交结果和真实余额；不绑定内部函数、组件结构或数据库查询写法。
- 复用已有 Phase 5 往来查询浏览器验收方式：在隔离 API 与数据库中通过公开接口创建业务，再由浏览器操作真实页面，覆盖余额、明细、来源返回与对账打印。补充查询失败、延迟和提交失败时的 UI 状态验收。
- 复用既有往来期初、退款与对账的 PostgreSQL／SQLite HTTP 集成契约组织方式，使用真实迁移和真实业务流水建立数据，核对汇总与资金办理后的结果。
- 建立超过一页的余额数据，令大额余额位于原始分页之外；验证四项全量总额与单位数量、前十名、降序分页、相同金额次序稳定，以及退款分类的绝对值金额。
- 覆盖同一单位双向、正负余额、零余额、无记录、停用及历史身份变化；验证两个方向不抵扣，零余额不计入待处理，无记录与结清仍可在全部查询。
- 浏览器覆盖默认客户应收、四项概览切换、图表方向切换与点击明细、搜索仅影响列表、全店范围说明、查询加载／空／错误与重试，以及明细返回保留分组、搜索和页码。
- 浏览器和真实 API 覆盖带入单位与办理类型、填入全额、部分金额、金额格式和超额提示、余额变化导致拒绝且保留输入，以及成功回执、继续登记、返回刷新和已结清移出待处理列表。
- 沿用资金幂等与并发契约验证重复提交不重复记账、余额校验基于最新状态；回归既有附件、冲销、来源追溯和期间对账打印的关键入口。
- 先定向验证 SQLite，再定向验证 PostgreSQL。新增双库 contract 分别使用 TestSQLite、TestPostgres 前缀，核对任务入口与 CI 各选中一次。如涉及 Schema，验证双库空库与旧数据升级。
- 实施后执行数据库兼容门禁（包含后端检查）、前端 lint 和 build；API 变更运行固定文档生成命令。报告未执行项及浏览器验收限制。

## Out of Scope

- 往来管理全部页面整体重做，期初录入或对账打印版式重新设计。
- 历史余额趋势、账龄、到期日、逾期判定、催款通知及自动收付款。
- 单据级款项分配、逐单核销、根据余额推断单张采购／销售单结清。
- 普通预收预付、客户与供应商自动抵扣、财务总账、银行余额和资金预测。
- 库存成本、毛利、基础报表、手机适配及其他未讨论的扩展。
- 附件能力新增、权限系统整体重构、业务单据生命周期变更。

## Further Notes

- Q1～Q9 的产品决策及测试边界均已确认，用户已授权发布与实施；发布时应用 ready-for-agent 标签。
- 本规格延续 Phase 5 往来查账能力，属于全店决策信息与操作路径的体验增强。GitHub 仍有既有往来任务处于打开状态，不能仅凭 issue 状态认定本地能力未实现。
- 统一往来单位及按总欠款收付款的既有 ADR 继续适用；本轮没有需要新增 ADR 的难以逆转取舍。
- 实施按本规格推进，完成后记录真实测试结果与尚未执行项。
