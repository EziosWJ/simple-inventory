# 采购入库、销售出库与往来明细：按查询条件导出 Excel 明细与合计

状态：已确认（2026-10-12）。已发布为 [GitHub #85](https://github.com/EziosWJ/simple-inventory/issues/85)。
范围：采购入库、销售出库、往来明细三页。任务拆分见 [导出任务](excel-export-tickets/README.md)。

本文件与 #85 内容一致；需求访谈的逐条决策见文末 Further Notes。

## Problem Statement

两名经营者目前只能在页面上逐页翻看采购入库、销售出库和往来明细的查询结果。想把某段时间、某个供应商或客户、某个商品的明细拿出来核对、留档或发给对方时，只能手工抄录或截图。跨单明细的数量合计与金额合计虽然在页面上能看到，但带不走；往来明细的期间余额也只能在屏幕上读，没有可交付的文件。

结果是每次月结对账、向供应商核对采购数量、向客户说明往来金额，都要重复一遍手工过程，而且手工抄录容易出错，抄漏一行就整份对账失去意义。

## Solution

在采购入库、销售出库、往来明细三个列表页各加一个「导出明细 Excel」按钮。点击后按**当前查询框的条件**把全部匹配明细导出为 `.xlsx` 文件。

每个文件包含两个 sheet：一个「明细」sheet（明细行，末尾一行金额合计与行数）和一个「合计」sheet（导出时间与查询条件、按状态的金额合计、按商品与单位的数量合计；往来明细为期间期初/变动/期末，多单位时为按单位的笔数与变动合计）。

文件由后端生成并以文件流返回，前端用已有的 blob 下载通道落盘。

## User Stories

**采购入库**

1. 作为经营者，我想按当前查询框的条件（供应商、商品、状态、交付方式、业务日期）导出采购明细，以便把某段时间的采购商品数量拿去核对。
2. 作为经营者，我想在采购页的「按单据」和「按明细」两个视图下都能直接点导出，以免必须先切换到「按明细」。
3. 作为经营者，我想让导出的商品型号和规格各占一列，以便在 Excel 里按规格筛选，而不是从拼接文本里挑。
4. 作为经营者，我想在明细末尾看到原金额合计与明细行数，以便一眼确认导出是否完整、有没有被截断。
5. 作为经营者，我想在合计 sheet 里看到按商品、单位、状态分组的数量合计，以便核对每件商品采购了多少。
6. 作为经营者，我想在合计 sheet 里看到草稿、已过账、已取消三种状态的金额合计，以便把有效采购和未过账草稿分开看。
7. 作为经营者，我想让采购明细带上有效退货数量与金额、净采购数量与净金额，以便把已退货的部分扣掉后再核对。
8. 作为经营者，我想让采购明细带交付方式（普通/直送），以便区分备货采购和直送业务。

**销售出库**

9. 作为经营者，我想按当前查询框的条件（客户、商品或服务、状态、交付方式、业务日期）导出销售明细，以便把某段时间的销售数量交给客户核对。
10. 作为经营者，我想让销售明细带上净销售数量和净销售额，以便直接使用已扣除有效退货后的数字。
11. 作为经营者，我想让销售明细区分实物商品与服务项目，以便知道哪些行不产生库存、也不能退货。
12. 作为经营者，我想让服务项目的退货列留空，以便一眼看出退货不适用于服务。
13. 作为经营者，我想让草稿和已取消销售的净额列留空，以便不会把无效销售当成有效销售统计。
14. 作为经营者，我想让导出的明细沿用页面上当前明细视图的排序（业务日期、成交单价、原金额、净销售额，含升降序），以便导出的顺序和我刚才在屏幕上核对的一致。

**往来明细**

15. 作为经营者，我想按选定的往来单位、客户或供应商方向、生效期间导出往来明细，以便把这段期间的每一笔金额变动交付给对方核对。
16. 作为经营者，我想在往来明细的合计 sheet 里看到期间期初、期间变动、期间期末，以便与页面上的一致性核对。
17. 作为经营者，我想只按关键词（多往来单位）导出，以便一次拿到某个名字相关的全部单位记录。
18. 作为经营者，我想在多单位导出时看到按往来单位与方向分组的笔数和变动合计，以便各单位余额分别检查。
19. 作为经营者，我想让往来明细带变动金额、前余额和后余额，以便逐笔验算余额衔接。
20. 作为经营者，我想让往来明细带业务日期与实际生效时间两列，以便区分业务日历日与实际记账时刻。
21. 作为经营者，我想让往来明细带实际操作人，以便知道每笔变动是谁录的。
22. 作为经营者，我想让往来明细带关联冲销单号，以便知道哪几笔是取消或冲销产生的。
23. 作为经营者，我想让往来明细带来源单号（采购单、销售单、退货单、收付款记录），以便回到原单据查证。
24. 作为经营者，我想在往来明细导出时不要求必须填完整期间，以便和页面查询保持同一套条件。

**文件本身**

25. 作为经营者，我想让导出的数量和金额是数值单元格，以便直接在 Excel 里求和、排序和做透视表。
26. 作为经营者，我想让业务日期与时间以文本写入，以便不出现时区偏移或格式被 Excel 改写。
27. 作为经营者，我想让不适用的单元格留空而不是写「不适用」，以便数值列的求和与透视不会被文字打断。
28. 作为经营者，我想让明细 sheet 第一行就是表头，以便选中整表直接做透视或复制。
29. 作为经营者，我想在合计 sheet 顶部看到导出时间、导出人和本次查询条件，以便日后证明这份文件是按什么条件导出的。
30. 作为经营者，我想让文件名带上前缀和日期范围，以便下载多个文件后能区分是采购还是销售、是哪段时间。
31. 作为经营者，我想让往来明细的文件名带上单位名或关键词，以便与其它单位的文件区分开。
32. 作为经营者，我想在匹配行数特别多时先被提醒，以便不会误点后长时间等待或者根本导不出来。
33. 作为经营者，我想在匹配行数超过系统上限时看到明确的中文提示，以便知道该缩小查询范围而不是以为功能坏了。
34. 作为经营者，我想在导出进行中看到按钮处于「导出中」且不能重复点击，以便不会点出多个文件。
35. 作为经营者，我想在导出失败时看到明确的中文原因，以便判断是查询条件问题还是系统问题。
36. 作为经营者，我想让导出不改变任何采购、销售、库存或往来数据，以便放心随时导出。
37. 作为经营者，我想让导出继续受现有菜单权限约束，以便不会因为新增导出而出现越权取数。

## Implementation Decisions

**接口**

- 三个独立子资源端点，查询参数与对应列表接口完全一致，响应为 `.xlsx` 文件流：
  `GET /api/v1/purchases/items/export`、`GET /api/v1/sales/items/export`、`GET /api/v1/partner-balances/entries/export`。
- 不复用列表端点加 `?format=xlsx`：同一 handler 混用 JSON 信封与二进制流会破坏现有 `ApiEnvelope` 约定。
- 不引入通用导出类型注册表或配置化导出框架。
- 参数校验复用现有 Service 的查询校验函数；校验失败仍返回既有 JSON 错误信封，文件流只在成功时返回。
- Swagger 注解需要同步维护，运行 `task api:docs` 并核对生成差异。

**取数**

- 采购与销售：在 repository 新增导出取数路径，复用现有明细查询构造器与排序函数，去掉偏移与条数限制，在同一个 `RepeatableRead` 只读事务内一次读取匹配行数、全部明细行与两个合计。这样文件内容与页面口径必然一致，且是单一快照，不会出现分页拼接导致的行间不一致。
- 往来明细：现有分页查询本来就是先把全部匹配行读入内存再切片，导出复用同一条取数路径，不新增 SQL。
- 后端硬上限 **100000 行**，超出返回 4xx，文案「匹配行数超过导出上限（100000 行），请缩小查询范围」。该值远高于前端确认线，只作为防止进程内存失控的安全阀。

**文件**

- 新增依赖 `github.com/xuri/excelize/v2`（MIT）。项目无 vendor 目录，不引入 vendor。
- xlsx 写入封装成一个小工具包，与既有平台层同放一处（`server/internal/platform/xlsx`），只提供「由 sheet 名、表头、行数据生成工作簿」的能力，列与数据由三个模块各自提供。
- 数量、金额、余额写数值单元格（金额套 `#,##0.00`；数量按最简小数写入，例如 `12.5`）；业务日期与时点写文本（`YYYY-MM-DD`、`YYYY-MM-DD HH:mm:ss`），导出日与导出时间按 `Asia/Shanghai` 计算，与前端展示时区一致。
- 不适用的单元格留空，不写「不适用」文字。
- 表头加粗、冻结首行、列宽按内容自适应。
- `Content-Type`：`application/vnd.openxmlformats-officedocument.spreadsheetml.sheet`。
- `Content-Disposition` 沿用现有文件下载的 `filename*=UTF-8''<urlencoded>` 写法，不额外提供 ASCII 回退名。
- 文件名：`采购明细_<起>-<止>.xlsx`、`销售明细_...`、`往来明细_<客户|供应商>_<单位名>_<起>-<止>.xlsx`、`往来明细_关键词_<关键词>_<导出日>.xlsx`；日期条件缺失时用 `全部` 占位，末尾补导出日。

**sheet 结构**

- 采购明细 sheet 列：采购单号、供应商、交付方式、业务日期、状态、商品编码、商品名称、型号、规格、单位、数量、成交单价、原金额、有效退货数量、有效退货金额、净采购数量、净采购金额。
- 销售明细 sheet 列：销售单号、客户、交付方式、业务日期、状态、商品编码、商品名称、型号、规格、类型（实物/服务）、单位、数量、成交单价、原金额、有效退货数量、有效退货金额、净销售数量、净销售额。
- 往来明细 sheet 列：往来单位、方向、类型、来源单号、业务日期、实际生效、实际操作人、变动金额、前余额、后余额、关联冲销单号、说明。
- 明细 sheet 第 1 行即表头；末尾合计行只填金额类与行数（例如「合计 | 共 1,234 行 | 原金额 ¥X」），数量与净额列留空——不同商品单位不同，跨商品求和无意义。
- 合计 sheet 命名统一为「合计」，明细 sheet 命名统一为「明细」。
- 数量合计沿用现有明细分组合计的口径（商品身份 + 单位 + 状态）。**不扩展**该结构增加型号与规格：不同规格本就是不同商品档案，编码加名称加单位已足以区分，且该结构同时服务于销售页面的「数量合计」弹层。
- 数量与单位分列写入（页面弹层是「12 支」拼在一起，Excel 里数值单元格必须与单位分开）。
- 往来明细导出不强制填写期间；统计区块只在「单单位 + 有期间」时给期初/变动/期末，否则给按单位的笔数与变动合计。

**权限与审计**

- 导出端点不加后端权限校验，与同类查询端点保持一致；权限继续由菜单码与 JWT 约束，前端按钮复用页面现有权限。若将来要统一为全部业务端点加权限，另立任务。
- 导出不写操作日志，与现有查询一致。

**前端**

- 按钮放在 `TableToolbar` 的 actions（`web/design-system/patterns/standard-list.md` 已规定刷新、导出等列表操作的位置），三页常驻一个「导出明细 Excel」按钮，与当前所在视图无关。
- 往来明细页当前的卡片头是纯文本容器，需要改为 `TableToolbar` 加 actions。
- 点击流程：先调一次现有列表接口取匹配行数；超过 10000 行时弹确认（「本次将导出 N 行明细，可能需要几秒，是否继续？」），否则直接下载；确认后请求导出端点，用现有 blob 通道取流并触发下载。
- 按钮点击后文案变「导出中」并禁用，完成或失败后复原。
- 失败提示三页统一用页面反馈组件（`notify`）。往来明细页当前未接该反馈组件，需要补上。
- 复用现有页面骨架组件，不新建列表组件或通用 CRUD 抽象。

## Testing Decisions

**好测试的标准**

只断言外部可观察行为：通过 HTTP 拿到 xlsx 字节流，用 excelize 读回后断言 sheet 名、表头、单元格值、明细行数与合计口径。不断言内部函数、SQL 文本或单元格写入的调用顺序——那些是实现细节，重构时会误报。

**接缝**

唯一的接缝是 **HTTP 导出端点**，沿用仓库已有的集成契约测试接缝（`server/integration`，对真实 PostgreSQL 与 SQLite 各跑一遍，通过 `app.Build` 组装真实路由与依赖）。这是三个页面共用的最高接缝，覆盖 处理器 → Service → Repository → xlsx 写入 的整条链路，不需要为 xlsx 工具包另开单元测试接缝。

**先例**

`server/integration/sale_item_query_contract_test.go` 的 `TestSQLiteSaleItemQueryHTTPContract` / `TestPostgresSaleItemQueryHTTPContract` 是直接先例（登录、造数、走 HTTP、断言 JSON）。同类还有 `inventory_contract_test.go`、`sale_purchase_sources_contract_test.go`。

**要写的测试**

- 新增契约测试分别使用 `TestSQLite` 与 `TestPostgres` 前缀，确认被 Taskfile 的 `db:integration:sqlite`（`^TestSQLite`）与 `db:integration:postgres` 各选中一次，双库各运行一遍。
- 覆盖场景：正常明细与两个合计 sheet 的口径、空结果、超过上限时拒绝、中文文件名与 Content-Disposition、往来明细的单单位期间模式与关键词多单位模式、数量与金额是数值单元格而日期是文本、不适用单元格为空。
- 前端不新增 `web/tests/*.mjs`。现有 `web/tests/sales-query-fixes.mjs`、`phase5-document-query.mjs`、`issue66-sale-query.mjs` 是按 `exact: true` 匹配「按单据」「按明细」按钮的回归面，新增按钮不得改变这些既有交互。
- 收尾检查：`task backend:check`、`task api:docs`、受影响的定向双库契约、`task frontend:lint`、`task frontend:build`。本改动属于局部查询，按 CLAUDE.md 验证分层不需要全量 `task db:check`。

## Out of Scope

- 不导出「按单据」视图的单据行，不做「单据 + 明细」多 sheet 一次性导出。
- 不做 CSV、不做导出模板定制或版式美化。
- 不扩展明细分组合计结构增加型号与规格。
- 不新增导出权限点、菜单或操作日志。
- 不把导出推广到采购退货、销售退货、库存流水、当前库存、往来余额等其它列表页。
- 不做导入、不做批量数据交换。
- 不改写历史文档（`docs/phase-4-plan.md` 的 Q32、`docs/phase-5-spec.md`、`docs/sales-query-spec.md`）中「不提供 Excel 导出」的阶段性排除项原文。
