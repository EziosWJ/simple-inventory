# Phase 3：库存余额、库存流水与库存调整

状态：已确认，Q1–Q20 已逐轮确认，Q21 已完成整体核对。

**GitHub 规格 issue：** [#7](https://github.com/EziosWJ/simple-inventory/issues/7) · `ready-for-agent`。按用户授权，规格及[六个纵向实现任务](phase-3-tickets/README.md)已直接发布。

## Problem Statement

经营者已能维护商品与服务、往来单位和唯一逻辑仓库，但不能录入现有库存、查询剩余数量或追溯数量变化。仅维护商品档案无法回答“还有多少”和“数量为什么变化”；直接覆盖库存数量又无法保留历史和纠错依据。

## Solution

经营者已经能维护商品与服务、往来单位和唯一逻辑仓库，但尚不能录入已有库存、查询剩余数量或追溯数量变化。本阶段提供库存调整单、当前库存和库存流水三个业务入口，先建立准确且可追溯的数量基础，采购与销售单据随后接入。

只管理实物商品数量，不管理成本、金额或逐台 SN。服务项目不参与库存，参考采购价不得用作库存成本。数量按商品基本单位计量，最多三位小数，库存始终不小于零。

### 核心用户路径

1. 录入已有库存：新建调整单，选择商品，填写增加数量，逐行选择“期初录入”，保存草稿，核对后过账。
2. 处理数量差异：填写增减数量和原因；一单可包含不同商品的不同增减方向，整单一起过账。
3. 查询库存：默认查看非零库存，包含停用商品；按商品关键词、分类、启用状态筛选，并可切换全部或零库存。
4. 追溯变动：从库存进入商品流水，查看每次变动及前后余额，打开来源调整单。
5. 纠正录入错误：草稿直接编辑；已过账单据符合取消条件时，填写原因取消，再新建正确单据；无法取消时，根据实物核对结果新建调整，在说明中注明原单号。

“期初录入”是增加库存的原因，共用调整流程；没有独立期初锁定、封账或历史日期补录。本轮不提供专门的盘点实存录入及差额自动计算。

## Implementation Decisions

### 调整单与状态

单据保存后由系统生成唯一、不可修改的单号；所有已保存单据均保留，不提供删除。

| 当前状态 | 操作 | 结果 | 库存变化 |
| --- | --- | --- | --- |
| 草稿 DRAFT | 编辑 | 保持草稿，更新版本 | 无 |
| 草稿 DRAFT | 过账 | 已过账 POSTED | 整单明细生效，生成原始流水 |
| 草稿 DRAFT | 取消 | 已取消 CANCELLED | 无，不产生库存流水 |
| 已过账 POSTED | 取消 | 已取消 CANCELLED | 整单生成反向流水，保留原流水 |
| 已过账或已取消 | 编辑 | 拒绝 | 无 |
| 已取消 | 重新过账 | 拒绝 | 无 |

每次取消必须填写原因。已取消单据保留取消前是否曾过账的信息；能够查询原过账和取消的操作人、时间。

草稿修改、过账和取消应针对用户所核对的最新版本。内容或状态发生变化时拒绝过期操作并提示刷新，避免将未核对的新版内容过账或覆盖。

单据至少包含一条明细，同一商品只能出现一次；明细包含商品、非零增减数量、原因和可选说明。一张单可以增加一种商品并减少另一种商品，不支持部分过账或部分取消。

| 明细原因 | 允许方向 | 说明 |
| --- | --- | --- |
| 期初录入 | 增加 | 系统接入时记录已有数量 |
| 盘盈 | 增加 | 补记实物多于账面的差异 |
| 盘亏 | 减少 | 补记实物少于账面的差异 |
| 报损 | 减少 | 因损坏等减少可用数量 |
| 其他 | 增加或减少 | 必须填写非空说明 |

明细原因约束适用于原始调整。取消冲销按原变动的相反方向记录，明确标记为取消冲销，关联原明细及流水，不能因冲销方向而误判原原因无效。

### 生效、取消和错误处理

只有过账及已过账取消改变库存。系统按实际生效时间记录流水，不支持倒签、修改流水或重算历史库存。

过账时重新校验商品为启用实物、基本单位和类型与草稿中用户确认的内容一致，并以事务内最新库存计算变动结果。任一明细无效、库存不足、写入或审计失败，整次操作回滚，草稿及库存保持原状。

取消已过账单据按原数量生成反向变动，使用原商品资料快照，无需商品重新启用；仍须校验每项反向变动后的库存非负。任一项失败，整单保持已过账状态，不留部分冲销。

例如先增加 10，再减少 7，现有库存为 3：取消增加 10 会导致负库存，必须拒绝。可以根据实物核对结果新建调整纠正，不能自动取消其他单据、删除流水或强制产生负库存。

实现必须保证重复请求或并发请求不会重复过账、重复冲销。对已完成的同一操作识别已有结果，对过期版本或相反状态返回明确冲突；客户端禁用按钮不能替代服务端一致性保证。

并发扣减须基于数据库事务内的实际余额：库存为 3，两张不同单据同时减少 2，最多一张能够过账。首次增加、同单并发过账、过账与取消竞争都不得丢失更新或产生重复流水。

### 商品引用与历史资料

- 停用商品不能加入新调整单，也不能在含有它的草稿中继续过账；需要调整时先启用。其库存、历史及取消已过账单据的入口仍保留。
- 草稿保存商品 ID 以及用户确认的类型、单位；类型或单位变化时拒绝过账，要求重新选择商品并确认数量，不自动换算。
- 商品产生过库存流水后，永久禁止修改类型和基本单位；归零、取消原单都不解锁。此前无流水的资料仍沿用 Phase 2 修改能力。
- 类型、单位修改与首次过账必须在并发情况下遵守同一限制，不能只在请求进入时查询一次历史再写入。
- 已过账明细和流水保留过账时的商品编码、名称、型号、规格、单位快照，历史不随当前资料编辑而改写；保留商品 ID 关联。
- 草稿核对界面展示实际将使用的商品资料，过账结果可查看最终快照；当前库存展示当前档案。商品描述字段可继续编辑。

ADR-0012 明确永久锁定的取舍：即使余额归零或原调整取消，旧流水仍需保留原类型和单位的含义；此后纠正这两个字段须另建正确档案，保留原历史。

### 查询与页面

| 页面 | 查询与展示 | 操作 |
| --- | --- | --- |
| 当前库存 | 编码、名称、型号、规格、分类、基本单位、当前数量、启用状态；关键词、分类、状态及非零/全部/零库存筛选 | 进入商品流水 |
| 库存调整 | 单号、状态、创建时间；按单号、状态、商品、创建时间筛选，分页；详情展示明细及创建/过账/取消记录 | 新建、编辑草稿、过账、取消 |
| 库存流水 | 按商品、发生时间、原始变动/取消冲销筛选，分页；展示生效时间、商品快照、增减数量、前后余额、原因、说明、操作人、来源单号 | 打开来源单据 |

无余额记录的实物商品在“全部/零库存”视图按零显示，不要求给每项商品预建库存记录。默认非零视图不显示这些商品，任何视图均不包括服务项目。

历史商品筛选以内部 ID 保持关联，允许从当前商品档案进入全部历史；流水和单据中的历史描述按快照显示。商品筛选后的单据不因包含多条明细而重复计数。

所有列表沿用现有分页约定，排序确定且稳定；时间筛选和日期展示约定在 API/界面一致表达。前端复用已有布局、列表和表单模式，不创建独立应用或新的设计系统。错误提示保留草稿输入，解释无效明细、库存不足和版本冲突；过账、取消前展示整单影响并进行确认。

### 登录、审计和事务

沿用 JWT 登录与菜单角色授权，业务入口接入真实菜单。所有已登录账号可访问库存接口、维护任意草稿、过账及取消；不新增操作权限或单据所有权约束，前端菜单隐藏不构成 API 授权限制。

每次成功的新建/编辑草稿、过账、取消及库存引用后的商品资料修改，与对应操作审计保持原子性。记录实际操作人，不把创建人当作后续操作人。过账与冲销的单据状态、库存余额、流水和审计必须在同一数据库事务内提交，失败整体回滚。

余额应与全部已提交原始流水和反向流水的累计数量一致；流水不可修改或删除，取消只追加反向记录。快照不改变商品的内部身份。

### 技术落地建议

以下是基于现有架构的实现建议；具体命名可在实现时调整，不改变已确认业务行为。

- 新增 inventory 业务模块，保持 Handler → Service → Repository，依赖在 internal/app 显式组装；Service 不依赖 Gin、GORM 或数据库方言。商品模块只增加必要的引用锁定校验，不做大范围重构。
- Repository 负责数据库事务和并发持久化，Service 负责业务规则与事务编排意图；复用已有 audit，不提前引入通用事务框架。
- 持久化概念包含调整单、调整明细、商品/仓库库存余额和不可变流水；草稿版本、原流水关联、唯一约束为过期操作和重复生效提供保障。
- 数量可采用有符号整数千分单位保存，API 使用十进制字符串，避免浮点解析及计算；拒绝零调整、超过三位小数和超出存储范围的输入，检查求和及取反溢出。
- PostgreSQL/SQLite 使用锁步的 Goose schema/seed 迁移，不改写旧迁移，不使用 AutoMigrate，API 启动不自动补种。数据库差异及并发策略局限在 repository/database/migration，SQLite 保持单 API 实例和小规模低写并发边界。
- 调整原因和单据状态可沿用现有系统字典展示；服务端按稳定业务编码校验状态流和原因方向，字典文字或排序变更不能改变库存规则。
- 新接口统一使用 `/api/v1/**`，沿用响应封装、分页及错误语义；所有注解与 Swagger 产物由源定义同步生成，不手改 generated 文件。

#### 当前仓库事实与实现注意点

- 当前 inventory 模块尚不存在。商品模块中 Store/Service 与模型定义位于同一小模块，持久化事务由 Repository 完成；新增锁定规则不要求先拆分现有小模块的文件布局。
- 当前商品 Save 的旧资料读取在事务外，实际更新与审计在 Repository 事务内；尚无商品版本字段或库存引用校验。商品类型/单位锁定须与库存首次过账协调，不能只补一次事务外查询。调整单版本检测属于本阶段新增能力。
- Service 实际在 API 启动入口显式构造，通过 `internal/app` 注册到已有认证路由；依赖接入延续现有入口，不引入隐式全局依赖。
- 当前双库 schema 最大版本为 00008，seed 为 00006；库存变更使用实现时下一个未占用且双库对应的版本。库存菜单、授权及字典新增 seed，不修改已执行的 Phase 2 seed。
- `task db:check` 的 PostgreSQL 筛选包含 Postgres，SQLite 筛选为 SQLite。新增 contract 可命名为 `TestPostgresInventory…` / `TestSQLiteInventory…`，并核对 CI 筛选；仅命名为 `TestInventory…` 可能被遗漏。
- 现有 SQLite 集成测试包含固定菜单数量断言，新增真实菜单后须同步更新；PostgreSQL 集成依赖 Docker，条件不满足时可能跳过，必须如实报告。
- Swagger 源注解和生成产物已存在，但未发现固定生成 Task；实现时使用对应工具重新生成并报告结果，不宣称已执行不存在的任务。

## Testing Decisions

主测试边界沿用现有应用 HTTP 路由连接真实数据库，优先使用这一最高公共边界；同一组场景运行 PostgreSQL 与文件型 SQLite。好测试验证请求、响应、提交后的业务记录及失败后是否改变，不断言私有函数、SQL 拼接或 GORM 调用顺序，也不为测试新增业务接口。

已有商品、往来单位、仓库的双库 HTTP contract，以及业务写入和审计失败回滚的集成场景可作为先例。主要覆盖 inventory 模块和 product 的引用锁定，不添加平行的多层重复测试。少量数量解析测试仅验证输入输出边界；前端使用实际用户路径验收及已有 lint/build，不承诺新增浏览器测试框架。

1. **录入与状态**：草稿不影响库存；单号唯一不可修改；多商品整单过账；重复商品、空明细、零数量、方向不匹配及其他原因缺说明均被拒绝；已过账不可编辑，已取消不可重新过账，无删除接口。
2. **数量精度**：0.001 等小数准确往返，空值、无效格式、超精度及溢出被拒绝，增减及冲销无浮点漂移；服务不进入库存。
3. **原子性与冲销**：一项库存不足导致整单失败；审计或流水写入失败全部回滚；取消草稿无流水，取消已过账单保留原流水且整单反向生效；负库存冲销被拒绝；余额与累计流水一致。
4. **并发与重复**：同单并发过账/取消只生效一次；首次增加不重复建立余额；并发扣减不超卖；过期草稿保存/过账/取消被拒绝；响应丢失重试不重复记账。
5. **商品约束**：停用商品不能选用或过账，但可查询并按约束取消历史单据；草稿类型/单位变化须重新确认；有流水后类型/单位永久锁定；首次过账与商品资料修改竞争不能绕过锁定；名称等编辑不改变历史快照。
6. **查询与追溯**：非零/全部/零库存与停用商品筛选正确；单据商品筛选不重复；原始和取消流水可分别查询，前后余额、来源、实际操作人及时间准确；未登录请求被拒绝，已登录账号访问范围一致。
7. **迁移与工具**：验证双库空库迁移、从 Phase 2 增量升级、schema/seed 版本及约束一致；检查新增业务测试实际进入数据库门禁；Swagger 从源重新生成。
8. **UI 路径**：实际操作“新建 → 保存草稿 → 编辑 → 过账 → 查库存/流水 → 取消”，覆盖混合增减、字段错误、负库存、停用资料和版本冲突；不为本阶段承诺新浏览器测试框架。

功能实现完成后执行 `task backend:check`、`task frontend:lint`、`task frontend:build`、`task db:check`，报告通过、失败和未执行项，不能把未运行的测试视为通过。
