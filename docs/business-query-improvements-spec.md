# 业务查询统一：采购、退货、库存与往来的筛选、明细和合计

## Problem Statement

经营者需要在采购、销售、退货、库存和往来查询之间连续核查业务，但各页面的筛选操作和列表表达不一致：部分页面选择档案后立即查询，部分需要提交；退货仍要求填写内部 ID；库存商品筛选占据较多空间；期初、收付款和退款记录使用有限数量的单位下拉框。商品或单位增加、改名、停用后，查找历史业务和恢复查询上下文不够直接。

采购、退货和库存调整列表缺少业务内容，经营者需要反复打开详情才能知道涉及哪些商品。采购历史成交价、跨单退货明细和全部筛选结果的数量或金额也缺少统一入口，容易将当前页、整单金额、匹配明细金额、净采购额和实际资金收付混淆。

销售出库的近期改动已经提供输入框内置浏览、可靠的查询状态、匹配明细标识、准确的过账影响及紧凑的列表合计。本规格将这些已验证的体验推广到相关业务模块，并补齐已确认的查询扩展。

## Solution

分三批交付业务查询改进：第一批采购入库和双向退货，同步销售筛选提交方式；第二批当前库存、库存流水和库存调整；第三批往来余额、往来明细，以及期初、收付款、退款记录。

筛选统一为可输入关键词、快速选择及输入框尾部浏览入口；选择或清除档案只填写待提交条件，点击查询或在主筛选输入按 Enter 才提交。查询条件、视图、排序、每页条数和页码可恢复，详情读取与列表查询隔离。

采购和双向退货支持按单据及按明细两种浏览，展示商品摘要、完整明细、真实匹配行和全结果合计。库存补充关键词历史查询及商品/单位数量合计。往来查询补齐适用筛选并保持客户、供应商方向及业务日期、实际生效日期的区别。过账和取消前准确展示本次库存与往来影响。

## User Stories

1. As an 个体店铺经营者, I want 在各业务查询页采用一致的筛选提交方式, so that 不必记忆每页不同的操作规则。
2. As an 个体店铺经营者, I want 输入关键词搜索商品或往来单位, so that 无需知道内部 ID 就能查业务。
3. As an 个体店铺经营者, I want 从输入框尾部打开分页浏览面板, so that 不知道准确关键词时也能找到档案。
4. As an 个体店铺经营者, I want 选中档案后看到名称、编码及必要规格, so that 确认筛选的是正确对象。
5. As an 个体店铺经营者, I want 清除或选择档案只改变待提交条件, so that 可以继续组合日期、状态等条件。
6. As an 个体店铺经营者, I want 点击查询或在主筛选输入按 Enter 提交整组条件, so that 主动决定何时更新结果。
7. As an 个体店铺经营者, I want 在候选面板内按 Enter 只确认候选或执行面板搜索, so that 不会同时误提交主列表查询。
8. As an 个体店铺经营者, I want 输入法确认、Esc、Tab及焦点恢复继续正确工作, so that 中文输入与键盘查找不被打断。
9. As an 个体店铺经营者, I want 查询商品或单位时精确 ID 与关键词互斥, so that 不出现难以理解的冲突条件。
10. As an 个体店铺经营者, I want 日期反向时收到提示且输入保留, so that 修正后继续查询。
11. As an 个体店铺经营者, I want 翻页、排序和刷新使用已提交条件, so that 尚未提交的输入不会偷偷影响结果。
12. As an 个体店铺经营者, I want 打开和关闭详情不覆盖待提交输入或重查列表, so that 连续核查业务时保持上下文。
13. As an 个体店铺经营者, I want 从详情、编辑及来源页面返回恢复原查询, so that 无需重新填写条件和定位页码。
14. As an 个体店铺经营者, I want 浏览器前进后退及页面重载恢复已应用条件, so that 可以可靠地往返查单。
15. As an 个体店铺经营者, I want 重置清空条件并查询默认范围, so that 可以重新开始查找。
16. As an 个体店铺经营者, I want 列表和合计明确显示加载状态, so that 不把上一轮数字当成新结果。
17. As an 个体店铺经营者, I want 查询失败显示错误和重试而非零合计, so that 不误判没有业务。
18. As an 个体店铺经营者, I want 迟到响应不覆盖最新查询, so that 快速操作后看到正确结果。
19. As an 个体店铺经营者, I want 结果减少后页码自动校正, so that 不停留在不存在的空页。
20. As an 个体店铺经营者, I want 每页选择 10、20 或 50 条, so that 按任务调整浏览量。
21. As an 个体店铺经营者, I want 查询排序稳定且金额按数值排列, so that 翻页和比较价格可靠。
22. As an 个体店铺经营者, I want 在采购单据列表直接看到商品摘要并展开完整明细, so that 就地核对采购内容。
23. As an 个体店铺经营者, I want 按商品查采购单时突出真正匹配的行, so that 知道这张单为何被查到。
24. As an 个体店铺经营者, I want 切换采购按明细视图跨单浏览, so that 查询商品历史采购价格和供应商。
25. As an 个体店铺经营者, I want 采购明细显示规格、单位、日期、数量、成交价和原金额, so that 辨认不同商品及不同成交条件。
26. As an 个体店铺经营者, I want 同商品不同成交价的原明细分别保留, so that 不丢失价格差异。
27. As an 个体店铺经营者, I want 已过账采购显示有效退货和净采购数量及金额, so that 了解退货后的采购结果。

29. As an 个体店铺经营者, I want 采购退货取消后净采购值恢复, so that 查询反映当前有效业务。
30. As an 个体店铺经营者, I want 草稿和取消采购单的原金额单独表达, so that 不把未生效内容当成有效净采购。
31. As an 个体店铺经营者, I want 采购合计覆盖全部筛选结果, so that 翻页不改变合计范围。
32. As an 个体店铺经营者, I want 在双向退货页搜索选择客户、供应商及原单, so that 无需填写内部 ID。
33. As an 个体店铺经营者, I want 退货按商品、状态、单号和业务日期组合筛选, so that 快速定位退货记录。
34. As an 个体店铺经营者, I want 退货单据显示商品摘要并可展开, so that 不打开详情也能辨认退回的商品。
35. As an 个体店铺经营者, I want 跨单查看采购和销售退货明细, so that 核对不同退货单中的商品、数量及金额。
36. As an 个体店铺经营者, I want 退货明细显示原成交价、本次数量及保存的退货金额, so that 核查累计取整下的实际退货结果。
37. As an 个体店铺经营者, I want 从退货记录打开原采购或销售单, so that 追溯原交易。
38. As an 个体店铺经营者, I want 按退货业务日期及状态查看全结果合计, so that 区分本期有效退货、草稿和取消内容。
39. As an 个体店铺经营者, I want 新退货继续从原单办理, so that 受原明细退货额度约束。
40. As an 个体店铺经营者, I want 按全部、普通或直送筛选采购、销售及退货, so that 分别核查交付方式。
41. As an 个体店铺经营者, I want 直送金额和成交数量纳入对应交易查询, so that 采购销售业务不会漏计。
42. As an 个体店铺经营者, I want 直送记录明确标识且不被表示为店内库存变动, so that 正确理解库存影响。

## Implementation Decisions

### 1. 模块与批次

- 第一批：采购入库、销售退货、采购退货，及销售查询交互同步。第二批：当前库存、库存流水、库存调整。第三批：往来余额、往来明细、期初往来、收付款及退款记录。按批次实现并验收，最终核对跨模块路径。
- 商品及往来单位档案的独立管理页面不纳入本次改造；共用选择器、查询状态和业务导航能力纳入，录单调用方必须兼容。
- 复用既有业务模块和公共组件，局部按职责整理；不引入通用 CRUD 框架或新的业务中间层。
- 遵守 Handler → Service → Repository 边界、显式依赖组装及 PostgreSQL/SQLite 双库支持。Service 不依赖 Gin Context、GORM 或具体数据库，方言差异局部化。
- 本次主要扩展只读查询及写入前的确认展示；既有库存、往来、审计、幂等、版本保护和状态流转继续适用。没有已确认的新业务表需求；确需 schema 或索引变更时使用同步版本的双库 Goose migration，禁止 AutoMigrate。

### 2. 统一筛选与状态

- 商品、客户、供应商及往来单位筛选采用直接输入、快速候选及输入框尾部浏览按钮。浏览入口常驻、可键盘聚焦、有可访问名称；文字、清除和浏览按钮互不遮挡。原单选择可按单号搜索，候选显示单位、日期、金额和状态。
- 主筛选区编辑、选中、清除只更新待提交条件；点击查询或主筛选输入的 Enter 提交。选择器活动候选的 Enter 确认候选，面板内部搜索的 Enter 只执行面板搜索；处理中文输入法确认，防止同时触发主查询。录单中的 Enter 不因此新增保存或过账行为。
- 每类档案的精确 ID 与关键词互斥，提交时归一化空白并沿用已有参数校验；用户不能看到互相矛盾的已应用模式。保持旧 ID 链接兼容。
- 待提交输入、已应用条件、视图分页排序、来源详情分别管理。非筛选 URL 参数变化不能覆盖待提交输入，开关详情不重查列表与汇总，详情读取只随来源 ID 或明确刷新变化。
- 翻页、排序、切换视图与刷新使用已应用条件。应用条件、切换视图、改变排序或页大小回第一页，单据及明细维护各自的分页和适用排序；待提交输入保留。已应用条件真正改变或明确重置时才同步输入。
- 已应用条件、视图、排序、页大小和对应页码保存到 URL。浏览器前进后退、页面重载、详情及编辑返回恢复上下文；重载不承诺保存尚未提交的输入。操作成功后刷新所返回列表及适用汇总，并保留上下文。
- 日期范围含所选首尾日，沿用项目北京时间业务日历及 UTC 存储转换。所有提交入口使用统一校验；无效条件阻止查询并保留输入。重置清空筛选及视图查询设置、回第一页并查询模块默认范围，不移除来源导航信息。
- 采购、销售和退货默认按单据、全部日期和状态、全部交付方式；库存保留非零库存默认范围，往来余额保留客户应收默认分类，往来明细仍需单位 ID 或关键词才查列表。重置不能把模块默认范围改成另一业务语义。
- 列表与合计明确表达加载、成功、失败和空结果。旧数字隐藏或明确标为上一轮结果；失败显示不可用和重试，成功空结果才显示零及空分组。过滤校验、列表读取、汇总和详情失败分别可见，迟到响应不覆盖最新状态。
- 刷新或业务动作导致页码越界时校正实际页并重查，URL、分页文本和记录一致；空结果回第一页。

### 3. 匹配与历史资料

- 沿用销售现有多词、大小写及字面特殊字符规则，实际支持字段与提示文字一致；不引入新的全文搜索体系。
- 采购、销售、退货、库存流水及调整单的商品关键词匹配当前商品档案及该记录已有商品快照；当前库存仅查当前档案。精确商品 ID 跨改名、停用继续关联同一商品。
- 采购、销售及双向退货的单位关键词匹配当前档案和单据已有历史单位名称；旧联系人、电话、品牌等只有真实保存的字段才能用于历史匹配，不补造未保存资料。往来余额及往来记录关键词仍匹配当前单位档案。
- 草稿显示已保存内容；已过账历史保留冻结快照及当时空值，不用当前资料回填历史描述。退货沿用既有退货来源及快照规则，不在查询时补造历史单位快照。
- 后端提供逐明细匹配标识或匹配明细 ID；前端不另写一套关键词匹配算法。无商品条件时不把所有行标为命中，当前档案命中也能标识对应历史行。
- 历史选择允许停用及身份变化对象，明确状态；新录单只选符合当前业务角色、类型及启用要求的档案。保留既有换选、参考价、人工价、资料变化确认和最近使用保护。

### 4. 单据、明细与合计范围

- 采购及双向退货新增或扩展公开的单据、跨单明细和全结果汇总查询，销售保留现有两视图能力。库存及往来扩展适用的筛选与汇总接口；旧接口调用保持兼容，继承既有认证和查询权限。
- 查询支持适用的单号、单位 ID/关键词、商品 ID/关键词、状态、业务日期、普通/直送、分页及允许的排序。退货另支持来源单 ID/单号，来源选择不限定于当前页。
- 单据分页每张单只计一次，匹配多行不能重复单据。展示整单金额、商品摘要及展开的全部明细，并突出真正匹配行。采购、退货及调整单保留适用原有动作和来源追溯。
- 跨单明细每条记录对应一条原业务明细，包含唯一身份、来源单身份及完整单号、单位身份及保存名称、业务日期、状态、交付方式、商品身份和快照、单位、数量、成交单价、行金额，以及该模块适用退货与净值信息；同商品不同价原行保持独立。
- 明细总数为匹配明细条数。商品条件按行匹配，不能把同单其他商品带入明细结果或明细合计；其他单据级条件限制来源单。
- 单据视图的合计统计匹配单据的整单内容，并明确标为整单金额或整单数量；明细视图的合计只统计匹配行。库存调整商品筛选返回整单，其数量合计统计匹配调整单的整单内容并明确标注，避免解释为筛选商品的数量。
- 例如一单含 A、B，按 A 查单仍显示整单及 A 命中，整单合计含 A、B；切到明细只显示和合计 A。对应计数分别写单据数或明细条数。
- 全结果汇总不受页码、每页条数和排序影响，由服务端准确聚合；不得只拉有限页面后伪装全量。列表、总数、汇总及有效退货口径一致，同一次查询不能读取到相互矛盾的业务状态。
- 采购、销售及双向退货增加全部/普通/直送筛选，默认全部，单据和明细显示直送标识。退货根据既有来源关系判定交付方式；金额和交易数量包含所选范围内的直送，不能解释为店内库存流量。

### 5. 采购净值与退货口径

- 已过账采购的有效已退数量和金额取截至当前仍已过账且未取消的采购退货，按原采购明细关联。净采购数量为原数量减有效已退数量，净采购额为原金额减有效退货金额。
- 日期筛选选择原采购业务日期，不限制关联退货日期。9 月采购 10 支、100 元，10 月有效退回 2 支、20 元，当前查 9 月净采购为 8 支、80 元；取消退货后恢复 10 支、100 元。页面明确标注截至当前口径，旧期间净值可随后续退货变化。
- 草稿及取消采购保留原数量和原金额，净值标为不适用，不计有效净采购；按草稿、已过账、已取消展示独立合计，已过账突出净采购额。
- 先按原明细聚合退货，再关联原采购；多笔退货不得倍增原数量、原金额或条数。金额使用已保存行金额，包含既有累计取整差额；不以数量乘参考价重算历史金额。
- 双向退货按退货自己的业务日期筛选。本次数量、原成交价、保存行金额及原单链接可见；草稿、当前有效已过账、已取消分别统计，已取消退货不再计入有效已过账合计。
- 采购净值查询和退货期间查询各自表达不同范围：原采购期间的截至当前净值，与所选退货期间发生的退货不能混称同一个指标。销售继续沿用已有净销售口径。
- 净采购额不表达实际付款、采购退款、库存成本或利润；客户和供应商收付款继续按单位方向总余额记录，不能推断单张采购或销售单是否结清。

### 6. 库存查询与数量合计

- 当前库存支持精确商品 ID 或关键词，保留分类、启用状态、非零/零/全部库存；仅列实物，停用商品按范围继续可查，从未建立余额记录的实物按零表达。展示当前档案及当前数量。
- 库存流水保留商品、业务来源、原始/冲销及实际生效日期范围，增加商品关键词。展示历史商品快照、单位、有符号变动、变动前后余额、来源、原因、生效时间、操作人和可追溯单号。
- 库存调整保留单号、状态、商品及创建日期范围，增加商品关键词、摘要和展开；明细包含实物规格、增减数量、单位和调整原因。调整单创建日期、库存流水生效日期保持明确标签，不能改称业务日期。
- 当前库存按商品 ID 及单位统计筛选范围当前数量；流水按商品 ID 及快照单位统计增加、减少及净变动，冲销按真实正负方向计入。流水合计不代表当前库存，也不额外承诺指定历史日期的库存余额复原。
- 调整单按状态、商品 ID 及单位分组表达增加、减少及净调整数量；草稿和取消内容标明未生效。取消单保留原单拟议增减量用于历史查询，不作为当前有效调整；实际取消冲销在流水合计按反向记录表达。
- 数量分组不因改名拆分商品身份，同名不同 ID 不合并，不同单位和状态分开。增加/减少按方向明确展示，净值有符号；无记录的分组为空。
- 所有数量合计入口置于结果或合计标题附近，通过弹窗查看全部分组，内容多时内部滚动。常用电脑宽度保证表格可读，窄屏弹窗可使用分组卡片；不静默截取前若干分组。

### 7. 往来查询

- 期初、收付款和退款的共用记录列表由固定数量下拉改为远程搜索及分页浏览，支持精确单位或关键词、客户/供应商方向、单号、适用业务类型、已生效/已冲销状态及业务日期范围。各业务入口仍限定其记录类别，不混入不属于该页的业务。
- 往来明细支持单位 ID/关键词、方向、来源单号及适用业务类型，继续按实际生效日期筛选，同时显示业务日期。冲销是追加的金额变动：筛选或展示必须保留原记录与反向记录的区别，不能因原记录已冲销而默认抹除它。
- 往来单位关键词按当前档案搜索；跨单位结果逐条标明单位和方向，前后余额按各自账户保留，不跨单位累计。来源单号及记录单号的输入标签与真实匹配范围一致。
- 只有指定一个单位 ID 及一个方向后，才能展示期间期初、变动、期末并打印对账单；期间汇总需要完整有效期间。关键词宽泛查询不生成跨单位对账单。
- 往来余额保留全店当前未结余额概览和欠款排名，明确不受下方列表搜索、分页影响。四类款项、全部范围、退款绝对值展示及按金额排序沿用既有规则。
- 同一单位客户和供应商方向分别保留，不自动抵扣；收付款和退款不分配到单据，不新增逐单结清标识。往来明细保留有符号金额和余额，突出变动及前后余额。
- 附件、附件留存历史、冲销、款项办理、来源打开及对账打印继续衔接；本批不改变这些业务写入规则。

### 8. 展示、分页、排序与精度

- 商品编码、名称、型号规格及单位保证可辨认；单位名称和客户/供应商名称保留可读空间。状态标签不换行，金额右对齐并使用等宽数字；单号使用较轻的链接，可缩略但能查看和复制全文。
- 采购和退货合计采用紧凑的状态卡片，金额为主、数量为辅；有效退货与净额标签对应其主要数值，避免负零及不适用值被显示为有效零。数量详情放弹窗，服务和不同单位不混算。
- 信息较多时在表格内部横向滚动，页面不整体溢出。常用电脑宽度下筛选和合计不挤压主要结果；窄屏只要求既有布局不溢出及内容可达，不扩展为完整手机产品。
- 所有本次查询列表提供每页 10/20/50 条。采购、销售、退货单据默认业务日期倒序；调整单按创建时间、库存及往来流水按实际生效时间倒序；往来余额保留分类金额倒序，当前库存保留适合商品列表的稳定次序。
- 采购、销售及双向退货交易明细支持日期、成交单价和行金额升降序；已有销售净额排序保留，采购可按适用净额排序。所有排序使用允许字段并以稳定身份消除并列，数值按精确数值排序，不能直接拼接任意用户 SQL。
- 单价及金额沿用人民币分和两位小数，数量沿用既有三位小数精度；服务端合计、排序与确认归集使用 decimal/定点，金额求和保存的行金额，不用浮点近似、不先合数量再乘单价。

### 9. 过账与取消影响确认

- 采购、双向退货、库存调整补齐过账确认，销售保留并回归已有准确确认。按商品 ID 和单位归集本次库存影响，展示编码、名称、型号规格及增加/减少数量，同商品分行可准确归集，同名不同商品不合并。
- 普通采购增加库存，普通销售减少库存，销售退货增加库存，采购退货减少库存；直送按既有业务规则无店内库存变化。服务不产生库存，零金额实物仍展示真实数量影响。
- 采购及退货确认同时表达供应商/客户方向余额的本次增加或抵减金额，零金额明确无往来金额变化；不得将抵减余额必然解释为尚有欠款或实际退款。
- 已过账单据取消确认展示原影响的反向内容、适用负库存/关联业务/退货顺序限制并要求原因。调整取消和往来记录冲销沿用各自业务语义；草稿取消明确无库存和往来变动。
- 确认表达本次变动，不承诺事后实时余额；服务端仍基于最新库存、往来、版本及关联业务校验。失败保留原因或输入并解释，既有不确定提交结果的核实和重试保护继续适用。
- 实际过账和冲销保持整单事务、不可变流水、审计及权限校验，展示扩展不能引入部分取消、部分过账或自动重放写入。

## Testing Decisions

- 测试边界待用户确认：以现有真实浏览器操作真实页面为主验收入口，复用公开 HTTP 的 PostgreSQL/SQLite 集成契约验证查询、全结果聚合和业务持久结果，不新增测试专用接口或内部实现入口。
- 好的测试断言用户可见内容、操作结果、公开 HTTP 响应、库存与往来实际状态；不绑定组件树、CSS 类名、私有函数、SQL 文本或内部存储布局。通过公开业务接口和真实迁移建立隔离夹具，不连接正式部署数据。
- 复用已有销售查询及整改浏览器验收、Phase 5 单据和往来查询、档案选择验收组织方式；HTTP 先例包括销售明细查询、单据关键词查询、双向退货过账、库存余额/流水、往来余额概览、实际生效时间及零金额契约。
- 浏览器覆盖本次所有模块的输入/候选/尾部浏览、选择和清除不请求主列表、Enter 两种上下文、中文输入法、停用资料、完整分页浏览、超过旧固定单位加载范围的选择、日期校验、重置、排序、页大小及前进后退。
- 组合验证未提交条件保留、选档案后立即填写日期再提交、切换视图、翻页、展开、来源/详情/编辑返回和刷新。检查详情请求随 ID 变化、开关详情不重查列表/合计，重复提交同条件能够明确刷新。
- 注入加载延迟、列表/合计/详情失败及迟到响应；验证错误可见且可重试、旧数字不冒充新合计、成功空结果零值、页面越界校正和 URL 一致。
- 双库使用超过一页的数据，包含多单位、多商品、多单位计量、同名不同规格、同商品不同价、同日多单、各状态、普通/直送、服务及零价实物；验证单据去重、行数、数值排序和分页变化下合计不变。
- 商品 A/B 同单夹具明确验证单据合计整单、明细合计仅匹配行及相应标签；调整单数量合计包含匹配单据的整单内容。验证服务与实物数量分组、改名身份归集及历史空字段保留。
- 采购契约覆盖多次部分退货、跨期退货、草稿退货、已取消退货、退货取消恢复净值、不同成交价对应原行及累计取整金额；验证 JOIN 不倍增和原采购期间截至当前口径。退货契约另验证自身业务日期范围、状态汇总和原单关联。
- 库存契约覆盖未建立余额、零库存、停用实物、历史关键词、正负变动、原始/冲销、调整各状态及合计；确认查询不修改库存，流水净变动不误作当前余额。
- 往来契约覆盖同单位双向、正负/零余额、历史身份变化、单位宽泛查询、类型及冲销状态、业务/生效日期差异；验证全店概览/排名不受列表条件影响、单单位期间余额和对账打印及附件/冲销来源可达。
- 通过真实页面与 API 验证过账/取消影响和实际结果一致，包含 0.1+0.2、同名不同商品、零金额、纯/混合服务、直送及冲销。复用受影响的失败回滚、负库存、版本冲突、关联业务、并发和审计契约，不为静态布局新增镜像实现的测试。
- 按项目验证分层确定执行范围。文档阶段仅运行 git diff --check；实现时前端执行 lint、build 及相关浏览器验收，后端执行检查，REST 变化同步源注解并运行固定 API 文档生成任务。
- 局部查询或聚合修改选择实际受影响契约，包括关联模块、失败回滚及并发，先定向 SQLite、再定向 PostgreSQL；新增契约用 TestSQLite/TestPostgres 前缀并核对任务及 CI 各选中一次。无匹配或必要用例跳过不算通过。
- schema/migration、公共 database/事务/锁修改或影响范围不能明确界定时执行一次全量双库门禁，migration 另验证双库空库与旧数据升级；CI 保留全量门禁。复用同批已通过且仍匹配实现的检查，不把定向通过描述为全量通过。
- 各批提供代表性电脑截图、数量弹窗/较窄窗口效果、实际检查记录和复跑入口，最终组合回归跨模块导航及销售原能力。经营者试用、自动浏览器验收和正式部署分别记录，不以自动通过冒充人工反馈。

## Out of Scope

- 商品和往来单位档案独立管理页面的重做；共用选择器的兼容调整除外。
- 库存成本、毛利、财务总账、业务趋势、贡献排名、补货建议及独立报表模块。
- 历史截止日余额或退货状态复原、固定结账报表，以及把原单期间截至当前净值当成同期间发生额。
- 单据级款项分配、逐单核销、账龄、自动抵扣、预收预付，或根据总余额推断单张单据结清。
- 服务退费、新退货办理入口、商品批量选择、自动合并明细或新的业务状态流。
- 筛选结果导出、新报表打印、送货单及对账单版式重做；已有打印及附件能力继续可用。
- 补造不存在的历史字段、修改冻结快照、增加档案历史回填或全局搜索引擎。
- 完整手机适配、权限体系重构、部署架构改造及正式服务器部署。
