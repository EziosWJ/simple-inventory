## Problem Statement

两名经营者共同经营个体店铺，准备在电脑浏览器上使用系统，但尚未投入真实业务。采购、销售、退货、直送、收付款和打印已有完整业务能力；日常录单仍需在弹窗中从有限下拉资料中挑选商品和交易对象，保存后再返回列表过账。查询虽然已有筛选与来源导航，停用资料却不易选到，工作台也没有常用业务入口。

两人分别登录并共享店铺业务时，需要看清数量、金额和状态，避免关闭页面丢失输入、覆盖另一人的修改，或因网络中断反复点击而重复建单。系统已有草稿版本保护和过账事务，但新建草稿及操作结果核实还不足以支撑可靠重试。

正式目标是云服务器使用；仓库已有发布构建和部分备份能力，尚缺完整的生产部署、每日整套备份、恢复和升级回退流程。本阶段先交付并隔离验收可部署版本，正式服务器上线另行安排。

## Solution

采购和销售采用完整录单页，按交易对象、业务资料、明细、合计及操作分区。以可分页的商品/往来搜索替代一次性加载的下拉选择，既能辨认同名资料，也能查询历史停用资料。提供“保存草稿”和“保存并过账”；过账前核对整单及库存、往来影响，失败保留输入，确认实际保存状态后安全重试。

沿用双人独立账号、共享店铺业务及真实操作人记录。版本冲突提供明确说明和重新加载最新内容入口；未保存离开需要提醒。完善欠款、往来明细和单据检索，工作台直接提供开采购单、开销售单、查欠款、查单据四类入口。

按录单与搜索 → 查询与首页入口 → 部署及备份恢复交付。生产准备采用 Linux 单机 Docker Compose、内嵌前端的 API、PostgreSQL 和 HTTPS 代理；补齐首次部署、账号准备、显式迁移、健康检查、升级与回退。每天自动备份，保留 30 天，提供异地复制步骤，并在隔离环境实际恢复数据库、上传文件和必要配置。

## Implementation Decisions

### 1. 领域边界与现有能力

继续采用模块化单体、Handler → Service → Repository、显式依赖组装、Goose 迁移和固定精度数量/金额。Service 不依赖 Gin、GORM 或具体数据库。修改商品、往来、采购、销售及查询的现有模块，复用库存、资金、审计、认证和打印能力，不重建领域模型或通用业务平台。

统一往来单位、唯一逻辑仓库、商品历史身份锁定、总余额结算和双数据库 ADR 继续适用。采购仅实物，销售可混合实物和服务或纯服务；同商品分行定价、非负库存、零金额单据、历史快照空值、直送与退货顺序、余额/退款约束和操作审计事务规则保持一致。只因界面迁移，不得改变已有业务规则。

### 2. 搜索与可辨认选择

优先扩展并使用现有商品和往来分页查询、按 ID 读取能力。关键词为首尾去空格后的字面片段，商品在编码/名称/品牌/型号/规格中匹配，往来在编码/名称/联系人/电话中匹配；拉丁字母的大小写行为在双库保持一致，百分号和下划线按输入文字处理，不作为数据库通配符扩展结果。排序稳定，页码、页容量与总数采用既有分页信封，不通过固定首批 500 条做客户端全量筛选。

录单时商品及往来均限定启用状态和正确类型/身份，过账仍做服务端复核。历史单据、余额和往来检索可包含停用资料；对历史对象不因其当前客户/供应商身份被移除而无法查到既有业务。选项绑定内部 ID；已选资料可独立按 ID 加载，不因当前结果页没有该 ID 而清空。

商品结果显示编码、名称、品牌/型号/规格、类型和单位；往来显示编码、名称、身份、联系人/电话及停用标识，空字段自然省略。搜索具有加载、空结果、失败、重试和翻页状态；切换关键词或筛选重置页码，迟到响应不能覆盖当前查询。复用一个适合不同业务筛选的选择能力，不引入全局搜索引擎、拼音索引或模糊纠错系统。

### 3. 完整录单页面与离开保护

采购/销售的新建与编辑使用可直接访问和刷新的独立业务路由。页面沿用既有标准表单、列表、详情模式及中性、高密度的设计规范；业务区域包含交易对象、日期/备注/销售送货资料、可增删的明细、准确合计、状态和明确操作。

保留当天本地日历日期、数量默认值、参考价带入、单位/类型变化确认、明确清空送货资料及同商品分行。详情、新建入口、历史编辑及直送创建销售入口均指向正确新页面；直送关联和旧打印链接不丢失。已过账/取消单不能作为可编辑草稿打开。

有未保存修改时，返回、菜单切换、内部跳转需确认，关闭或刷新浏览器使用原生离开提醒能力；已成功保存且无新增修改时不误提醒。保留输入的承诺针对当前页面仍存在的失败或冲突场景，不新增完整表单本地自动暂存、离线编辑或跨设备草稿同步。

### 4. 保存草稿、请求重试与结果查询

现有新建/编辑草稿接口保留原有行为和版本规则；为新页面增加同一次提交的稳定请求标识和结果查询能力，接口使用现有业务 API 范围与响应信封。稳定请求标识使用 `requestKey`，新页面每次确定提交生成一个，首尾去空格后非空且最多 100 字符。旧客户端未提供该字段时仍可按原约定提交，但不宣称其新建请求具备幂等保障。

幂等范围为操作人、采购/销售业务类型及创建/编辑操作；编辑还绑定目标单据及提交时版本。第一次有效提交在同一数据库事务中保存草稿、明细、真实操作审计和持久请求结果关联；请求指纹涵盖所有业务输入，数量/金额按已验证精度规范化，保留同商品明细的顺序和不同报价、送货空字符串与省略的含义。并发相同请求只产生一份结果；同键不同内容返回明确冲突，不覆盖或追加另一份内容。失败回滚不留下成功回执。

重复相同请求返回原操作结果对应的单据 ID、提交结果版本及最新状态信息，不再次写业务或成功审计。结果查询必须能够区分已提交、尚未确认及确定未提交；请求查无结果并不在原请求仍可能执行时立即等同于失败。操作结果查询按原操作人授权，业务单据仍由两人共享，不能将请求回执权限误变成单据所有人隔离。

编辑回执需能在原修改之后又发生另一人的修改/过账时，说明原提交是否成功及当前状态；不能仅靠当前内容相等猜测成功。操作标识在结果明确前持续关联当前操作，可保留最小恢复标识以便刷新后核实；不持久化整张未保存表单，也不把旧账号的恢复标识带入新登录用户。结果明确后若用户改变内容，按新操作和正确版本提交。

请求记录由采购/销售业务负责，只引入保障上述行为所需的持久关联、指纹和结果信息，不设计全系统幂等框架。schema 变更采用双库逻辑同步的增量迁移，旧单据、明细 ID、版本、流水、快照、审计及已有接口保持可读可用。

### 5. 保存并过账与不确定状态

两个按钮清楚区分保存草稿与保存并过账。提交前确认拟保存对象、日期、明细数量/价格、合计及库存/往来方向影响；取消确认不触发提交。确认后先安全保存草稿，再以该保存结果的同一单据 ID 和版本调用现有整单过账；不新增同时过账直送采购/销售的能力。

保存失败不继续过账。保存成功但库存不足、资料变化或其他过账失败时保留该草稿、单号和输入，明确显示尚未过账及失败原因，可编辑或重试；不删除已经保存的草稿，不将保存与过账误承诺为一个可回滚的整体操作。

网络中断或响应丢失时先核实保存回执与单据实际状态。尚无法确认时展示核实状态，避免再次新建、盲目过账或误报成功；可以主动重查和在确认条件允许后由用户重试。已有过账事务及版本保护继续使库存、往来、状态和审计只生效一次；重复过账的既有冲突响应可保留，新页面据最新事实展示已过账、已取消或版本变化。

如果另一人改变草稿，停止使用旧确认继续过账；如果单据已取消，不自动重新创建或重新过账。纯服务、零价商品、全零金额、同商品分行和直送关联依旧按原规则处理。前端禁用重复点击是体验保障，不能代替数据库唯一性、版本和事务保障。

### 6. 双人编辑与真实账号

两名经营者各自使用独立账号，沿用已有已登录业务访问范围，共享店铺单据和往来，不新增按创建人、岗位或所有人过滤。真实菜单配置要使两人的日常入口可用，既有认证和系统管理规则不被 mock 显隐替代。

保存和过账以版本条件执行。冲突保留用户输入，说明另一人已修改/过账/取消，提供重新读取最新内容的明确操作；丢弃未保存修改前确认。重新读取后沿用最新状态和版本，终态显示只读，不自动合并、覆盖或反复提交旧版本。记录实际执行人；重试不能将第一次成功操作的执行人替换为后来查询者。

### 7. 查账、单据和首页入口

采购/销售列表沿用单号、交易对象、状态、商品和业务日期筛选，统一查询/重置/翻页体验，修改条件不会继续使用旧页码；从详情或来源返回可恢复原查询上下文。多行商品匹配不会重复计数。历史选项含停用和已失去当前身份的对象，资料展示仍区分当前档案与已过账快照。

欠款查询以往来单位及客户/供应商方向表达。客户正余额表示客户欠店铺，负余额表示店铺待退客户；供应商正余额表示店铺欠供应商，负余额表示供应商待退店铺。两个方向不相互抵扣，不根据总收付款计算单张单据已结清或账龄。

余额 → 对应方向明细 → 来源业务的路径保持对象、方向和期间上下文，覆盖期初、采购/销售、退货、收付款、退款及冲销。期间余额仍按实际生效时间，业务日期另行显示；现有收付款及对账打印继续可用。工作台四类动作直接到对应页面，查单据入口可明确选择采购/销售；不新增报表或跨业务全局搜索。

### 8. Linux 单机部署及首次账号准备

交付生产用途的 Compose 编排，API 使用内嵌前端的发布产物，独立 migration 工具显式执行，PostgreSQL 为部署数据库，HTTPS 由反向代理提供。提供可复现的配置模板、构建/启动步骤、持久存储及版本标识，复用既有发布方式，不改变日常开发入口。

正式运行显式选择生产环境并关闭 Swagger；外部访问通过 HTTPS 代理，代理配置与可信代理设置一致，API 和数据库留在部署内部网络。就绪检查验证数据库，不能只用存活接口判定可接入业务。说明真实域名/证书准备及续期；隔离验收可用受信任的测试证书验证代理和浏览器访问，不伪称已取得真实服务器证书。

数据库、上传文件及必要配置持久化，重建容器保留业务；迁移失败不继续放行业务。首次部署的账号步骤在受控访问下完成管理员初始凭据替换及两名独立业务账号准备，演示两人真实菜单、共享单据及实际操作人。配置模板不含真实密码或密钥，备份/输出不泄露凭据；不新增用户岗位权限或重写整个账号管理模块。

提供按版本升级、备份、显式迁移、启动及冒烟步骤。回退以发布前整套备份加旧应用版本恢复，不承诺 migration down 或旧二进制直接读取已升级 schema。实际正式服务器、DNS、证书签发和业务数据迁入在后续上线安排中执行。

### 9. 每日整套备份、保留与恢复

生产部署包提供每日自动执行的备份任务，可手动触发相同流程。使用与服务端主版本匹配的 PostgreSQL 工具生成可验证的逻辑备份，同时归档上传文件和必要部署配置、发布版本及校验信息；不复制运行中的 PostgreSQL 数据目录作为逻辑备份。

数据库与上传文件须对应同一可恢复业务状态。允许安排维护窗口或暂停应用写入来取得一致集合，步骤明确中断及恢复方式；不额外承诺无停机备份。输出只有全部步骤成功且基本校验通过才标记为成功，失败产生非零结果及可查日志，不将临时或半份产物用于恢复；失败后仍应恢复正常业务运行条件。

保留最近 30 天的成功完整备份，清理仅作用于本部署明确归属的备份目录和完整备份，不删除源库、上传目录、配置或不明文件，不因当次失败删除最近可用备份。备份和必要配置权限受控，提供复制到另一设备/存储及完整性核对的步骤，不自动连接尚未指定的外部服务。

每日频率允许故障后补录最多约一天的数据；尚未执行异地复制时不能宣称具备服务器整体丢失后的异地恢复能力。隔离恢复使用新库和新持久目录，按记录的版本恢复配置、数据库及上传文件；验证就绪、独立账号登录、单据/明细/快照、库存与往来流水及余额、文件可读和打印。演练须真的导入并运行，不只列出备份文件或恢复工具目录。

## Testing Decisions

### 测试边界

沿用 Q22 已确认的最高公开边界：真实 React 浏览器 → 认证 HTTP API → 文件型 SQLite 或隔离 PostgreSQL；部署和恢复由隔离 Compose 环境及恢复后的浏览器/HTTP 验证。复用既有 Phase 4 HTTP 契约、真实 UI/PDF 和数据库门禁，不为了测试新增业务旁路或暴露内部函数。

测试只断言用户可观察结果、持久业务状态和失败时的原子性，不镜像组件实现或 SQL 语句。造数及故障控制可使用既有夹具与测试代理；实际录单、搜索、确认、冲突处理、查账、导航和打印通过页面操作完成。真实场景测试可读取数据库核对流水/审计及版本，但不得仅用直调 Repository 替代公开请求。

### 必须覆盖的行为

1. 超过 500 条商品和往来档案，编码/名称/品牌/型号/规格/联系人/电话片段，中文及字母大小写，字面百分号/下划线，同名结果、分页、已选 ID 不在当前页、空结果/失败/迟到响应；录单类型/身份/状态与历史停用查询分开。
2. 采购及销售完整页面的新建、编辑、刷新及实际菜单/直送入口；默认日期、参考价、单位确认、送货空值、同商品分行、服务、零金额；离开未保存内容的确认行为。
3. 保存草稿无库存/往来影响，保存并过账确认后原子业务生效；保存失败不触发过账，过账失败同一草稿可继续，打印入口仍指向正确已保存单据。
4. 服务端已提交而响应丢失的新建、编辑、过账；同键同内容并发及重复提交、同键不同内容冲突、过程失败无成功回执、回执与审计原子性、请求结果在重启后仍可核实。旧单据和未提供 requestKey 的旧调用继续可用。
5. 两个真实登录会话读取同一版本，先保存者成功，旧版本保存/过账拒绝且保留输入；确认加载最新内容后按新版本操作；原提交成功后又被另一人修改/过账/取消的结果核实。
6. 单号/对象/商品/状态/日期查单据、历史停用及身份变化、多行计数、分页/重置、详情返回条件；客户/供应商正负余额语义、按实际生效期间的明细、完整来源追溯和原有结算操作。
7. 送货单显示/隐藏金额、草稿标记、过账快照含空值及多页；对账全期间、多页及冲销。实际输出 PDF 核对 A4 尺寸、页数、页码、边界、末页合计和签收等既有要求。
8. 隔离部署空库初始化、显式迁移、HTTPS 页面/API及深链接刷新、独立账号共享业务、生产 Swagger 关闭、数据库就绪、重建容器后持久性；部署模板和日志不含真实凭据。
9. 手动触发每日备份同一流程，成功/失败/重复运行、30 天归属范围清理、数据库与上传的一致恢复、配置权限、复制后校验；恢复到新库和新目录后核心读取、写入及打印验证；发布前备份和旧版恢复的升级回退演练。

### 门禁与人工验收

新增数据库契约分别使用 TestSQLite… / TestPostgres… 前缀，确认 Taskfile 和 CI 各选中一次。数据迁移同时验证双库空库、Phase 4 旧数据升级、逻辑版本同步和菜单断言；保留旧快照、版本、请求记录、流水和审计。REST API 同步源注解，并按固定入口运行 task api:docs 检查生成差异。

实现交付执行 task check、task db:check，生产内嵌构建再执行 task build:check，并完成隔离部署和恢复演练。定向调试先 SQLite，再 PostgreSQL；最终集中门禁，记录通过、失败、跳过和未执行项。

父母在隔离环境用代表性业务分别登录，完成采购、销售、查欠款、查往来及追溯原单；记录实际完成情况和困难，必要时回到对应任务修正。自动检查通过与试用材料准备完成不等于父母已试用。阶段验收报告分别列技术检查、恢复演练和人工试用状态；人工未执行时明确待人工，不宣称适合正式启用。

## Out of Scope

- 经营报表、库存成本、毛利、SN、服务退费、财务总账及银行账户余额。
- 手机专项适配、原生客户端、离线填单、完整表单自动暂存、跨设备编辑同步及多人自动合并。
- 新增岗位权限细分、按创建人隔离业务、多组织、多仓或多副本高可用架构。
- 批量导入、Excel 导出、历史成交价辅助、专用连续录单快捷流程、全局全文/拼音/纠错搜索。
- 普通预收预付、逐单核销/账龄、应收应付自动抵扣、折扣/运费/税额独立计算。
- 一键联合过账直送两单、重新设计真实退货与取消规则、历史库存倒签或重算。
- 打印模板改版、电子签名、签收附件及尚未选入的其他 Phase 4 范围外能力。
- 自动外部存储接入、PITR/分钟级恢复、无停机备份或发布、数据库间存量转换。
- 本次正式云服务器部署、DNS/真实证书变更、真实业务数据迁入，以及将人工试用冒充自动完成。

## Further Notes

- 需求依据为本轮 Q1～Q22 已确认规划；本规格细化可观察行为和工程契约，不将现有 Phase 4 能力重复当作新功能。已交付的 Phase 4 修复不因远程 issue 尚未关闭而重复创建任务，也不在本次改动旧 issue 状态。
- 开发任务应按可演示的完整采购、销售、查询或部署路径拆分；共用能力随首个使用场景落地，不建立独立的大范围架构重构任务。真正技术阻塞与阶段推进顺序分别记录。
- PostgreSQL 的逻辑备份提供数据库一致快照；将它与上传文件及配置组成整套恢复资料，需要本部署另行协调业务写入。依据 [PostgreSQL pg_dump 官方说明](https://www.postgresql.org/docs/current/app-pgdump.html)。
- 发布规格与任务不代表实现或阶段验收完成；父母实际试用及正式上线仍需按已确认边界执行。
