## 本阶段交付

目标是让两名经营者在电脑浏览器上顺手完成日常录单与查账，并形成后续云端正式启用所需的可部署版本。实际首批使用者为用户父母两人，系统尚未用于真实业务。

| 方向 | 已确认交付 |
| --- | --- |
| 采购/销售录单 | 独立完整录单页，清晰展示交易对象、明细、合计；提供保存草稿及保存并过账，过账前核对整单及库存/往来影响，离开前提醒未保存内容。 |
| 商品及往来搜索 | 商品按编码、名称、品牌、型号和规格片段搜索；客户/供应商按编码、名称、联系人和电话片段搜索；结果可辨认，录单遵守启用及身份规则，历史查询可选停用资料。 |
| 查询及入口 | 改善欠款/往来查询、按单号/交易对象/日期检索单据及来源追溯；工作台提供开采购单、开销售单、查欠款和查单据入口。 |
| 保存可靠性及双人协作 | 两个独立账号共享业务；保留实际操作人。失败保留输入并核实实际状态，已保存而未过账的内容保留为草稿；重试不重复建单或过账。版本冲突明确提示，加载最新内容前确认未保存修改。 |
| 部署及恢复 | Linux 单机 Docker Compose，包含 API、PostgreSQL、HTTPS 代理及显式迁移步骤；提供首次部署、账号准备、健康检查、升级及回退说明。每天自动备份，保留 30 天，提供异地复制步骤并实际恢复数据库、上传文件和必要配置。 |

实现顺序：录单与搜索 → 查询与首页入口 → 部署及备份恢复。本阶段在隔离环境交付和验收可部署版本，正式云服务器上线另行安排。

## 范围边界与验收

- 暂缓经营报表、库存成本/毛利、手机适配、岗位权限细分、批量导入、历史成交价辅助和专用连续录单功能；Phase 4 的其他范围外事项未因本次规划自动纳入。
- 已有采购/销售、直送、服务混合销售、分行定价、退货、收付款及退款的业务规则继续沿用；已有送货单和对账单打印保持可用并做回归。往来仍按总余额记录，不根据收付款推断某单结清。
- 每日备份的恢复目标允许故障后补录最多约一天数据；异地复制按交付步骤执行，本轮未约定自动对接外部存储服务。
- 真实浏览器覆盖完整录单、搜索、过账确认、欠款/往来查询及来源追溯；包含同名资料、停用资料、超过原 500 条资料加载上限的检索、未保存离开、保存及过账响应丢失、重复提交及双人编辑冲突。
- 数据相关变更通过 PostgreSQL/SQLite 契约与事务验证，保持双库支持；实现时执行 `task check`、`task db:check`，REST API 变更按固定入口运行 `task api:docs`，schema 变更使用双库 Goose migration 并验证空库及旧数据升级。
- 在隔离环境验证部署及真实备份恢复，再安排父母用代表性业务完成录单、查欠款及追溯原单，记录能否完成操作和实际困难；人工试用结果不得由自动检查代替。

- 采购/销售草稿已有版本号保护：保存携带读取时版本，成功后版本递增；旧版本保存或过账被拒绝，不覆盖另一人的修改。前端出错保留输入，但缺少专用重新加载最新草稿的动作。
- 当前过账事务保证同单只生效一次；重复请求返回冲突，不返回第一次成功结果。响应丢失时前端尚无主动查询实际状态的完整体验。
- 新建草稿尚无请求幂等键，响应丢失后再次创建可能产生重复草稿。改善保存流程时需要将此情况作为明确验收场景，而不能只靠禁用按钮。
- 当前录单弹窗未提供离开前未保存提醒。以上事实来自 `purchase/repository.go`、`sale/repository.go`、`purchases.tsx`、`sales.tsx` 及公共表单组件的只读核查。
