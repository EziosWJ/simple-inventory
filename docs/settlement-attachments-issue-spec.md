# 往来管理：收付款、退款与期初录入可选附件

规格发布为 [GitHub #63](https://github.com/EziosWJ/simple-inventory/issues/63)；用户随后授权本地实施，结果见 [交付记录](settlement-attachments-acceptance.md)。以下保留发布时的规格内容。

## Problem Statement

经营者录入客户收款、供应商付款、销售退款、采购退款以及期初应收／应付时，无法保存对应截图或付款单据 PDF。凭证散落在聊天和本地文件中，查账、协作和追溯冲销记录时难以找到依据，历史业务也需要补充附件。

## Solution

三个入口增加可选的 PNG、JPG/JPEG、PDF 附件，每条记录最多五个有效附件，单个最多 10 MB。支持新建上传、保存后补传与移除、历史记录补传；列表显示数量，详情支持预览、下载和附件历史。经营者按业务权限共享附件；移除保留原文件和操作信息，冲销后只读。附件操作不改变往来金额。

## User Stories

1. 作为经营者，我希望客户收款时附上转账截图，以便核对收款依据。
2. 作为经营者，我希望供应商付款时附上付款单据 PDF，以便追溯付款凭证。
3. 作为经营者，我希望销售退款时附上退款凭证，以便核对退还客户的款项。
4. 作为经营者，我希望采购退款时附上供应商退款截图，以便核对收到的退款。
5. 作为经营者，我希望期初应收记录附上欠款佐证，以便追溯启用系统前的客户欠款。
6. 作为经营者，我希望期初应付记录附上欠款佐证，以便追溯启用系统前的供应商欠款。
7. 作为经营者，我希望没有附件也能保存，以便及时录入业务。
8. 作为经营者，我希望同一记录支持多个附件，以便同时保留截图和完整单据。
9. 作为经营者，我希望清楚看到格式、大小和数量限制，以便选择合适文件。
10. 作为经营者，我希望不合规文件被明确拒绝，以便修正后重试。
11. 作为经营者，我希望看到逐文件上传状态，以便确认上传结果。
12. 作为经营者，我希望已选附件失败时暂不保存新业务，以免误认为凭证已完整保存。
13. 作为经营者，我希望失败时保留表单和成功项，以便只重试失败项。
14. 作为经营者，我希望主动移除失败项后能继续保存，以便处理暂时无法取得的凭证。
15. 作为经营者，我希望保存后补传迟到的银行回单，以便补齐业务依据。
16. 作为经营者，我希望历史记录也可补传，以便逐步整理旧凭证。
17. 作为经营者，我希望补传失败不影响已有业务和附件，以便安全重试。
18. 作为经营者，我希望列表显示有效附件数量，以便快速判断凭证是否齐备。
19. 作为经营者，我希望在记录详情集中查看附件，以便直接找到对应材料。
20. 作为经营者，我希望放大截图，以便看清转账时间和金额。
21. 作为经营者，我希望打开 PDF 查看，以便核对完整单据。
22. 作为经营者，我希望下载附件，以便提供原凭证给交易对方。
23. 作为经营者，我希望移除选错的附件，以便当前详情只展示适用凭证。
24. 作为经营者，我希望移除项不占五个名额，以便上传正确文件。
25. 作为经营者，我希望附件历史仍可查看移除文件，以便追查纠正过程。
26. 作为经营者，我希望知道上传和移除的操作人及时间，以便追溯协作操作。
27. 作为经营者，我希望按业务权限查看和管理对方上传的附件，以便共同经营店铺。
28. 作为经营者，我希望权限不足者不能通过文件地址访问凭证，以便保持业务访问范围。
29. 作为经营者，我希望补传和移除不改变金额、业务日期或余额，以便整理凭证不影响账务。
30. 作为经营者，我希望冲销后原记录附件只读并保留，以便追溯原业务。
31. 作为经营者，我希望冲销继续只填写原因，以便沿用现有纠错流程。
32. 作为经营者，我希望网络重试不重复记账或重复绑定附件，以便安全保存。
33. 作为经营者，我希望并发补传或冲销仍满足数量与只读规则，以便多人操作时保持一致。
34. 作为经营者，我希望通用文件管理不会误删业务凭证，以便有效和历史附件一直可查。
35. 作为经营者，我希望恢复备份后仍能读取有效和历史附件，以便恢复完整业务资料。

## Implementation Decisions

- 修改往来业务模块、文件管理模块及三个业务页面，复用现有文件存储、上传和鉴权读取能力。附件归属具体业务记录，不只依赖模块标签表达归属。
- 仅支持 PNG、JPG/JPEG、PDF，服务端校验扩展名和实际内容，沿用现有图片完整解码及像素限制。单文件上限采用 10 × 1024 × 1024 字节，并在界面说明；每条最多五个有效附件，移除项不计数。
- 新建表单可选多文件，显示文件名、大小、逐文件状态和错误。未选附件正常保存；仍在上传或存在失败项时阻止保存，保留表单和成功项，支持重试或主动移除失败项。
- 上传暂存后随业务保存绑定；业务记录、关联和审计在同一数据库事务中生效，失败不部分记账。沿用业务幂等机制，保存重试不重复记账或绑定。
- 已保存未冲销记录可补传、移除，包括历史记录。多文件补传逐项反馈结果，保留成功项，失败不影响原业务或既有附件。
- 列表显示有效数量，详情提供有效附件及历史入口；图片可放大，PDF 可打开，全部支持鉴权下载。移除项普通详情隐藏，历史仍可查看原文件及操作信息。
- 新增持久化关联，记录所属业务、文件、有效／移除状态、上传及移除操作人和时间。现有通用审计未持久化具体资源 ID 和摘要，不能只依赖通用日志；关联变更和审计需事务一致。
- 冲销后原记录有效及历史附件均只读；冲销反向记录不提供附件入口，凭证从原记录追溯。事务内校验状态和数量，防止并发超过上限或在冲销后变更附件。
- 经营者按对应业务权限共享附件，不限制上传者本人。查询权限允许查看、下载、历史查阅；录入权限允许补传、移除。前后端均落实授权，不能以菜单显隐代替后端检查。
- 复用现有权限模型明确查询与录入操作的对应授权；附件的直接文件访问也受业务权限约束。通用文件删除、批量删除、停用等入口不得绕过已绑定及历史绑定文件的留存保护。
- 未绑定暂存文件需要安全清理，不能中断有效表单重试，不能清理已移除或已冲销记录的附件。备份恢复覆盖关联元数据、历史和原文件。
- 保持 Handler → Service → Repository 边界，Service 不依赖 Gin Context、GORM 或具体数据库。双库 Schema 变更使用同步的 Goose migration；不使用 AutoMigrate。
- 扩展业务保存请求支持上传附件引用，查询响应支持有效附件数量及详情；增加补传、移除、历史和鉴权文件读取契约。具体接口命名遵循现有 REST 约定，旧请求不带附件时保持兼容。
- 同步 API 源注解，使用项目固定命令重新生成并审查 Swagger。接口命名、关联表布局和临时清理调度由实施者在上述约束内确定。

## Testing Decisions

- 用户已确认：以现有业务 HTTP 接口的双库集成测试为主；浏览器测试补充三个页面的上传、失败重试、预览和历史操作。
- 测试验证外部行为：HTTP 结果、业务余额、有效数量、历史信息、文件可访问性及权限拒绝；不绑定内部函数调用或复制实现逻辑。
- 优先复用现有期初往来、退款与对账、业务幂等和双库 integration contract 的组织方式，通过实际业务 HTTP 链路连接真实测试数据库和临时文件存储。文件内容、multipart 与大小边界可补充现有文件 Handler 测试，不新增测试专用业务接口。
- 覆盖三种入口与客户／供应商方向：无附件保存、新建绑定、历史补传、列表数量、详情、图片及 PDF 预览、下载、移除历史和操作人时间。
- 覆盖精确大小边界、第五／第六个有效附件、移除后名额释放、非法格式及伪装内容，确保服务端限制生效。
- 覆盖上传中、上传失败、重试、移除失败项后继续保存、事务回滚与幂等；补传失败不能破坏既有业务及附件。
- 覆盖并发数量限制、冲销与附件操作竞争；已冲销记录不能补删，原有效及历史文件仍可读取。
- 覆盖未登录、权限不足、按文件标识直接访问及通用文件管理绕过尝试；验证留存保护。
- 覆盖未绑定文件清理和备份恢复，确保有效、移除、冲销记录的附件不丢失。
- 浏览器沿用现有业务 UI 自动化方式，验证三页表单与状态、数量、预览下载、历史及冲销只读。模拟请求验证 UI 状态，真实 API 链路另验文件读取。
- 先定向验证 SQLite，再验证 PostgreSQL，覆盖空库 migration 和旧数据升级。新增双库 contract 分别使用 TestSQLite、TestPostgres 前缀，核对 Taskfile 与 CI 各选中一次。
- 实施后运行双库门禁及前端 lint/build；双库门禁包含后端检查。更新 API 后生成文档，报告未执行检查和验收限制。

## Out of Scope

- 库存期初录入、采购单和销售单附件，冲销记录独立附件入口。
- 其他文件格式、OCR、银行流水识别、自动识别金额或自动记账。
- 普通预收预付、逐单核销、财务总账和银行余额。
- 全项目权限重构、匿名上传、独立附件平台、对象存储迁移。
